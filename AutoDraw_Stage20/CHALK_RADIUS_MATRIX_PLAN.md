# План измерения расхода CHALK по радиусам кисти

**Статус:** ACTIVE — подготовка к эксперименту.  
**Дата:** 31 октября 2026 г.  
**Ветка:** `feature/image-geometry-optimization`  
**Назначение:** определить экспериментальную зависимость фактического расхода игрового CHALK от радиуса кисти.

## 1. Подтверждённая исходная точка

Первый валидный live-прогон после исправления корреляции:

- сценарий: `paint_consumption_long_lines`;
- радиус: 1;
- 6/6 штрихов;
- геометрия: 6 горизонтальных линий по 400 логических px;
- суммарная длина центральных траекторий: 2400 px;
- `pointCount`: 1 → 719;
- точный расход: 718 CHALK;
- сумма sampled `pointDelta`: 718;
- dropped events, monitor dropped events и monitor errors: 0;
- `monitor_capture=saved`.

718 — результат только этого радиуса и сценария. Не считать его универсальной нормой и не выводить из него формулу для остальных кистей.

## 2. Неизменяемая геометрия теста

Использовать существующий сценарий `paint_consumption_long_lines` без изменения координат:

- доска: 460×240 логических px;
- 6 отдельных горизонтальных штрихов;
- каждый штрих: от X=20 до X=420;
- Y: 18, 54, 90, 126, 162, 198;
- шаг между центральными линиями: 36 px;
- длина одного штриха: 400 px;
- суммарная центральная длина: 2400 px.

Между измерениями запрещено менять план, масштаб браузера, ROI доски, параметры executor и любые настройки, кроме радиуса кисти.

## 3. Матрица радиусов

Измеряемые радиусы: **1, 5, 10, 15, 20, 25, 30**.

Три независимых блока (21 прогон):

| Блок | Последовательность радиусов |
|---|---|
| 1 | 1 → 5 → 10 → 15 → 20 → 25 → 30 |
| 2 | 30 → 25 → 20 → 15 → 10 → 5 → 1 |
| 3 | 10 → 20 → 30 → 1 → 15 → 25 → 5 |

Порядок блоков фиксирован заранее. Он уменьшает вероятность связать конкретный радиус только с началом или концом длительной сессии.

## 4. Протокол одного прогона

1. Убедиться, что Game Monitor bridge подключён и сессия активна.
2. Очистить доску штатным workflow AutoDraw.
3. Проверить пустую доску по эталону; если очистка не подтверждена — остановить прогон.
4. Зафиксировать baseline `pointCount` и `max` после очистки.
5. Установить заданный радиус.
6. До рисования подтвердить фактическое значение через `AutoDrawGameMonitor.status().snapshot.radius`.
7. Запустить неизменённый `paint_consumption_long_lines`.
8. Дождаться завершения 6/6 штрихов.
9. Зафиксировать post `pointCount`, получить monitor run и привязать его к точному executor window.
10. Сохранить отдельный experiment manifest, execution report и monitor report.
11. Проверить отсутствие ошибок/потерь и совпадение CHALK delta с суммой sampled `pointDelta`.
12. Очистить доску и подтвердить восстановление перед следующим прогоном.

Каждый прогон — отдельный experiment. Не складывать pointCount между разными прогонами и не считать reset счётчика отрицательным/положительным расходом.

## 5. Условия принятия результата

Прогон валиден только при одновременном выполнении всех условий:

- executor завершил 6/6 штрихов;
- имеются точные `started_at` и `ended_at` executor;
- найден ровно один monitor run в executor window;
- `stroke_count=6`;
- `brush_radius_status=single`;
- `observed_brush_radii=[заданный радиус]`;
- `chalk.status=exact`;
- `post_point_count >= pre_point_count`;
- `post_point_count - pre_point_count = consumed_points > 0`;
- `sampled_point_delta_total = consumed_points`;
- dropped events = 0;
- monitor dropped events = 0;
- monitor errors = 0;
- нет reset, неоднозначности или посттестовой активности внутри выбранного run.

Не использовать визуальную оценку полоски краски вместо pointCount. Неполная траектория не отменяет точный CHALK counter, но её нельзя использовать как полную геометрическую длину пути.

## 6. Ограничение ресурса и остановка

Если расход одного прогона достигает 80% максимальной квоты либо игра сообщает о достижении лимита/неполном исполнении, остановить дальнейшие повторы этого радиуса и сначала разобрать результат. Не допускать продолжения после признака исчерпания квоты.

Невалидный прогон сохраняется как артефакт с причиной исключения. Его нельзя заменять чужим monitor run, усреднять с валидными результатами или записывать как нулевой расход.

## 7. Анализ после сбора

Для каждого радиуса показать все три первичных измерения, среднее, медиану, минимум/максимум и разброс. Отдельно показать CHALK на весь сценарий, на один штрих, на 100 логических px центральной длины, FPS, длительность, число sampled points и статус траектории.

Сначала проверить повторяемость внутри радиуса. Только после этого сравнивать радиусы и строить модель. Не предполагать линейную зависимость от радиуса.

## 8. Подготовка к браузерному этапу — обязательные изменения

До первого локального браузерного прогона необходимо:

1. Добавить в experiment manifest метаданные серии, блока повтора, номера повтора и заданного радиуса.
2. Добавить уникальную идентификацию прогона, чтобы один Game Monitor run нельзя было прикрепить к двум experiment.
3. Проверить защиту от старых, посттестовых и неоднозначных runs; при отсутствии точного совпадения результат должен быть unavailable.
4. Добавить сводный анализатор матрицы, который группирует только валидные результаты по радиусу и повтору.
5. Добавить unit/regression tests на метаданные, дедупликацию run, валидацию измерения, пропуск невалидных результатов и расчёт статистики.
6. Запустить локальные Python tests и тесты WebSocket bridge. Проверить GitHub Actions для нового HEAD.

**Браузерный gate закрыт до завершения пунктов 1–6.** Когда изменения будут готовы, пользователю нужно отдельно сообщить, что требуется открыть локальный AutoDraw, игру и Game Monitor bridge для live-проверки. Без доступной локальной браузерной сессии эти измерения нельзя симулировать.

## 9. Запреты

- Не добавлять ручные линии в TEST_CASES или матрицу.
- Не менять геометрию контрольного сценария между радиусами.
- Не приписывать результат одному радиусу, если Monitor увидел несколько.
- Не считать путь равным расходу CHALK.
- Не строить универсальную модель по одной точке.
- Не изменять `master`; все изменения выполнять в `feature/image-geometry-optimization`.
