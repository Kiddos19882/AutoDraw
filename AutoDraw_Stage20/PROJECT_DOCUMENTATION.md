1. **`README.md` — навигация и быстрый старт.** Коротко объясняет назначение приложения, Windows-запуск и указывает на основной справочник. Не дублировать в нём архитектурные подробности.
2. **`PROJECT_GUIDE.md` — технический источник истины.** Содержит подтверждённые факты о коде, форматах, алгоритмах, ограничениях, тестовых данных и измерениях. Исторические записи сохраняются, но верхний блок текущего состояния должен быть единственным актуальным статусным блоком, а не соседствовать с устаревшими альтернативами.
3. **`MASTER_ROADMAP.md` — источник истины по очередности и статусам работ.** Здесь должны быть текущие приоритеты, зависимости, критерии закрытия и ссылки на специализированные планы. Он не должен повторять длинные технические объяснения из справочника.
4. **Специализированные документы** (Game Monitor, brush lab, временный outline-first plan) — подробные протоколы, методики, результаты и незавершённые задачи соответствующих направлений.
5. **Технический аудит, аудит рефакторинга и readiness** — датированные исторические снимки. Они полезны как объяснение, почему принимались решения, но не должны использоваться как описание текущего HEAD без повторной проверки.
6. **`REFACTORING_PLAN_2026-10-29.md`** — план и журнал его выполнения. После появления `MASTER_ROADMAP.md` не должен самостоятельно конкурировать с ним за роль актуального списка приоритетов.
7. **`CI_VERIFICATION_2026-10-30.md`** — журнал исторических CI-проверок. Последние результаты должны ссылаться на конкретный SHA и job; текущий статус HEAD удобнее поддерживать в одном месте — в `PROJECT_GUIDE.md` и кратко в `MASTER_ROADMAP.md`.
8. **`PROJECT_ANALYSIS_PLAN_10_STAGES.md` и `PROJECT_DOCUMENTATION.md`** — отдельный контур настоящего аудита. Первый управляет этапами, второй хранит их результаты; они не заменяют пользовательскую документацию продукта.

Такая схема позволяет сохранить все полезные исторические материалы, не удаляя их ради искусственного сокращения количества Markdown-файлов.

## 3.2. Фактическая точка входа и запуск

Основной entry point — `AutoDraw_Stage20/integrated_app.py:main()`.

Последовательность запуска:

1. Импортируется `integrated_app.py`; вычисляется `APP_ROOT` с учётом frozen/portable режима.
2. `ensure_import_paths()` добавляет каталоги `source/preparation` и `source/executor` в `sys.path`.
3. `configure_environment()` формирует общие пути пользовательских данных и устанавливает переменные окружения `AUTODRAW_*`.
4. После настройки путей импортируются модули обеих подсистем и UI вкладок. Это сделано намеренно: модули читают пути хранения при импорте.
5. `main()` создаёт каталоги данных, создаёт единственный `tk.Tk()`, экземпляр `AutoDrawUnifiedApp`, затем запускает `root.mainloop()`.
6. `launcher.py` — тонкая совместимая точка входа: импортирует `integrated_app.main` и вызывает её.

Важное следствие: `integrated_app.py` — не только UI-компоновщик, но и composition root приложения. Он отвечает за порядок настройки окружения, разрешение импортов, создание хранилищ/путей и связывание подсистем callback-ами.

### Архитектурная схема верхнего уровня

```text
launcher.py
   |
   v
integrated_app.main()
   |
   +--> configure_environment() / ensure_import_paths()
   |
   +--> AutoDrawUnifiedApp (одно Tk root, один mainloop)
          |
          +--> AutoDrawWorkbench (подготовка / проекты / профили)
          |       |
          |       +--> shared_image_processing.pipeline
          |       +--> stage8_optimizer / stage9_quality
          |       +--> autodraw_project / profile_manager
          |
          +--> Stage6App (область / загрузка плана / исполнение)
          |       |
          |       +--> geometry_models.DrawingPlan
          |       +--> drawing.mouse_executor.MouseExecutor
          |       +--> drawing.color_plan_execution (цветные планы)
          |
          +--> PaletteDetectionTab
          +--> PaletteQuantizationTab
          +--> ColorScanlineTab
          +--> PaintLimitTestTab
          +--> BrushBehaviorTestTab
          +--> BrushCalibrationTab
                  |
                  +--> callback-и и общие пути данных
   |
   +--> data/ (profiles, palettes, projects, results, runtime, logs)
```

Схема показывает основные зависимости и не означает, что все алгоритмы подготовки вызываются последовательно при каждом запуске: цветовая ветка, одноцветная ветка, тестовые вкладки и калибровка являются отдельными пользовательскими сценариями.

## 3.3. UI и границы подсистем

В `AutoDrawUnifiedApp.__init__()` создаётся один `ttk.Notebook` с восемью верхнеуровневыми вкладками:

1. Подготовка изображения.
2. Исполнение рисунка.
3. Палитра браузера.
4. Преобразование в палитру.
5. Цветной scanline-план.
6. Тест лимита краски.
7. Тест кистей.
8. Калибровка теста.

Внутренний `AutoDrawWorkbench` имеет собственный Notebook из пяти вкладок: изображение, растровый план, качество, проект/экспорт, профили. Таким образом, интерфейс вложенный: главное окно координирует специализированные вкладки, а workbench сохраняет внутреннее разделение этапов подготовки.

Подсистемы создаются в едином процессе и получают Tk root/родительский Frame, пути данных и callback-и. Отдельных процессов для подготовки и исполнения нет. Это упрощает передачу объектов в памяти, но увеличивает связность composition root и делает порядок инициализации значимым.

## 3.4. Основные потоки данных

### A. Одноцветный план

```text
Исходное изображение
  -> load_rgb_image()
  -> crop / fit_to_canvas()
  -> grayscale / denoise / contrast / brightness / threshold
  -> ProcessingResult (prepared_color, grayscale, binary_mask)
  -> build_scanline_plan(binary_mask)
  -> DrawingPlan-compatible dict
  -> analyze_quality(binary_mask, plan)
  -> write_validated_execution_plan()
  -> JSON в data/runtime/
  -> DrawingPlan.load() / Stage6App.load_plan_from_path()
  -> проверка границ и преобразование к области экрана
  -> MouseExecutor.execute()
  -> execution report в data/results/
```

Фактический конвейер обработки реализован в `shared_image_processing/pipeline.py`; старый путь `source/preparation/image_processing/pipeline.py` оставлен тонким compatibility wrapper. Подготовка и проверка качества выполняются в UI-потоке синхронно; автоматического фонового worker для тяжёлой обработки в проверенном пути не обнаружено.

### B. Цветной план

```text
Подготовленное цветное изображение
  -> PaletteDetectionTab: получение/сохранение профиля палитры
  -> PaletteQuantizationTab: приведение изображения к палитре
  -> ColorScanlineTab: цветной scanline или geometry plan
  -> план + именно тот palette_profile, который использовался при построении
  -> integrated_app._transfer_color_plan_to_executor()
  -> сохранение в data/runtime/
  -> Stage6App: загрузка типа плана и профиля
  -> проверка размера/палитры/экранного снимка (preflight)
  -> MouseExecutor + ColorPlanExecutionHooks
  -> отчёт с hash плана, выбранными цветами и диагностикой
```

Важное архитектурное решение: цветной план передаётся вместе с документом профиля палитры из того же состояния вкладки, которое создало план. Это предотвращает случайное применение другого профиля, выбранного позднее на соседней вкладке.

Поддерживаются разные типы цветного плана: `autodraw_color_scanline_plan` и `autodraw_geometry_color_plan`. Для geometry plan используется отдельный сериализатор/валидатор. Адаптивный план кистей — отдельный sidecar и на текущем кодовом пути допускается только для scanline-плана; его безопасность дополнительно проверяется перед преобразованием к DrawingPlan. Это не подтверждает фактическую безопасность кисти в игре.

### C. Тесты кисти и лимита краски

Тестовые вкладки не реализуют отдельный низкоуровневый исполнитель. Они формируют/сохраняют тестовый план, проверяют совпадение размера плана и выбранной области, затем используют существующий `Stage6App` и его `MouseExecutor`. Для теста кистей приложение требует ручного подтверждения фактического значения кисти в браузере перед запуском. После завершения callback маршрутизирует отчёт обратно в Brush Behavior Test UI.

Это снижает дублирование механизма управления мышью, но создаёт особую ответственность у `integrated_app.py`: он определяет, какой тип плана сейчас загружен и как обрабатывать callback завершения.

## 3.5. Модели и архитектурные границы

- Общие геометрические сущности вынесены в `geometry_models/`: `Point`, `Stroke`, `DrawingPlan`.
- В `source/preparation/models/` и `source/executor/models/` сохранены совместимые import wrappers; проверки импорта подтверждают, что обе стороны экспортируют общие классы, а не независимые реализации.
- Общий image-processing pipeline вынесен в `shared_image_processing/pipeline.py`; прежние пути подготовки/исполнителя — обёртки.
- `DrawingPlan` хранит локальные координаты холста, штрихи, порядок и метаданные. Экранные координаты не входят в модель: исполнитель прибавляет к локальным координатам X/Y выбранной области.
- Цветные планы имеют отдельные схемы и валидаторы; перед низкоуровневым исполнением они конвертируются в `DrawingPlan`, а данные цвета остаются отдельным execution context.
- `profile_manager.py` описывает workspace profile, экранную область и параметры калибровки. Stage 6 по-прежнему имеет собственные файлы target profile и execution settings; unified app синхронизирует их через callback-и, а не через единый объект профиля в памяти.

Границы между алгоритмическими модулями в целом различимы, но UI-компоненты и orchestration остаются тесно связаны через прямые ссылки на внутренние поля и методы друг друга (например, `workbench.plan`, `palette_quantizer.result`, `color_scanline_tab.plan`, `executor.area`, приватные методы `_notify_area_change()`, `_select_area()`, `_refresh_execution_plan()`). Это рабочая схема, но она делает рефакторинг UI рискованным: изменение внутренних имён/контрактов затрагивает composition root.

## 3.6. Импорты и разрешение модулей

Подтверждённая особенность — использование коротких абсолютных импортов (`from stage13_workbench import ...`, `from stage6_execute_plan import ...`, `from models import DrawingPlan`, `from drawing.mouse_executor import ...`) при добавлении каталогов подсистем в `sys.path`.

- `ensure_import_paths()` вручную меняет глобальный порядок поиска модулей.
- Preparation добавляется в начало `sys.path` после executor, поэтому preparation становится первым компонентным каталогом поиска.
- Одинаковые короткие имена модулей в разных корнях создают зависимость от порядка `sys.path` и рабочего способа запуска.
- Тесты `test_import_resolution_diagnostics` подтверждают ожидаемое разрешение коротких импортов и идентичность общих моделей/pipeline на проверенном CI пути.
- На текущей проверке циклическая зависимость, которая гарантированно приводит к рекурсивному импорту, не установлена. Но без отдельного полного import graph нельзя объявлять отсутствие всех циклов доказанным.
- Это не пакетная архитектура с единым namespace: компоненты подготовки и исполнения фактически являются каталогами, добавляемыми в глобальное пространство импортов Python.

**Оценка:** это существенный источник скрытой связанности. В первую очередь следует сохранять существующие wrappers и тесты разрешения импортов; удаление wrappers или перестройка namespace без полной проверки portable build не обоснованы.

## 3.7. Потоки, события и жизненный цикл исполнителя

GUI работает в главном Tk-потоке. Обычная подготовка изображения, построение плана и оценка качества выполняются синхронно в обработчиках Tk. Исполнение мыши вынесено в daemon thread `AutoDraw-Executor`; отдельный daemon thread используется для визуального теста кисти.

Жизненный цикл стандартного исполнения:

1. `Stage6App._start_execution()` проверяет наличие плана/области, валидирует настройки, границы, текущий экран и профиль цветной палитры.
2. До запуска блокируются элементы управления, `running=True`, создаётся новый `threading.Event` для остановки.
3. Worker создаёт `MouseExecutor`, при цветном плане — `ColorPlanExecutionHooks` с preflight и before_stroke callbacks.
4. `MouseExecutor.execute()` запускает глобальный F12 listener, выполняет обратный отсчёт, preflight, затем проходит штрихи в сохранённом порядке.
5. Для каждого штриха выполняются переход к началу, mouseDown, интерполяция движения с заданным шагом и задержками, end hold, mouseUp.
6. Остановка проверяется между точками и во время interruptible waits. PyAutoGUI FAILSAFE остаётся включённым.
7. В `finally` выполняется последняя попытка mouseUp и останавливается keyboard listener; результат возвращается как summary.
8. Worker ставит UI callback через `root.after(0, ...)`; основной Tk-поток обновляет прогресс, сохраняет execution report и возвращает состояние кнопок.

Зафиксированные защитные механизмы:
- нельзя заменить план/область во время активного исполнения;
- F12 и Stop используют общий stop event;
- задержки прерываемые;
- mouseUp выполняется после каждого штриха и повторно в общем cleanup;
- ошибка mouseUp переводит выполнение в failed и отражается в отчёте;
- для цветного плана перед стартом выполняется preflight проверки палитры;
- закрытие окна при работающем исполнителе запрашивает остановку и откладывает уничтожение root до callback завершения.

Архитектурные риски:
1. Worker вызывает `self.root.after()` из фонового потока. Это используется для маршалинга UI-обновлений, но Tkinter не является thread-safe API; поведение при одновременном закрытии окна/уничтожении Tcl interpreter нужно проверять отдельными тестами на Windows.
2. Потоки daemon: аварийное завершение процесса может прервать задачу, не дождавшись cleanup; штатный close flow старается остановить исполнение, но принудительное завершение ОС/процесса не покрывается.
3. `running` — обычный флаг, которым управляет UI-поток; worker не должен самостоятельно менять UI state. В проверенном основном потоке завершение маршрутизируется обратно через `root.after`.
4. Подготовка изображения и построение плана синхронны в UI-потоке; большие изображения/планы могут временно заморозить интерфейс. Это архитектурное наблюдение, не измеренный performance defect.
5. Отдельного универсального task manager/очереди фоновых задач нет; orchestration построена на прямом создании `threading.Thread`, `threading.Event` и callback-ах.

## 3.8. Хранение данных и передача между подсистемами

Unified app централизует пути в `data/`:
- `profiles/` — workspace, target area, execution settings и калибровка;
- `palettes/` — профили браузерной палитры;
- `projects/` — проекты `.autodraw`;
- `results/` — отчёты, конверсии, тесты;
- `runtime/` — текущие промежуточные планы передачи;
- `logs/` — каталог журналов.

Между вкладками используются два способа передачи:
- in-memory callbacks/accessors для текущего результата, плана и профиля;
- JSON-файлы в `data/runtime/` для передачи плана executor-у и сохранения совместимого контракта.

Одноцветный план перед публикацией записывается во временный JSON, загружается обратно как `DrawingPlan`, проверяется по границам и только затем атомарно заменяет целевой runtime-файл. Цветные планы сохраняются соответствующими сериализаторами и валидируются на загрузке Stage 6.

Формат `.autodraw` — ZIP bundle с manifest, ограничениями размеров, проверкой состава и хешей. При открытии заявлено отсутствие распаковки произвольных путей; это отдельный механизм проекта, а не формат runtime-передачи executor-у.

## 3.9. Найденные архитектурные проблемы и риски

### A-01. Ошибка создания каталога вместо файла калибровки кисти

В `configure_environment()` путь `brush_calibration` включён в общий словарь `DATA_PATHS`, но он обозначает JSON-файл `data/profiles/brush_paint_calibration.json`, а не каталог. Функция специально пропускает его при создании директорий. Однако `integrated_app.main()` затем без фильтра вызывает `mkdir(parents=True)` для каждого значения `DATA_PATHS`, включая этот файл-путь.

В результате обычный запуск может создать каталог с именем `brush_paint_calibration.json`. Затем этот же путь передаётся в `BrushCalibrationTab` как путь к JSON-файлу. Чтение/сохранение калибровки в такой ситуации может завершиться ошибкой `IsADirectoryError`.

**Статус:** подтверждено статическим чтением кода; реальный запуск для подтверждения последствий не выполнялся.  
**Приоритет:** высокий, так как затрагивает сохранение/загрузку профиля калибровки теста кисти.  
**Рекомендация:** в отдельной задаче исправить создание каталогов так, чтобы файловые пути исключались; добавить regression test на структуру `DATA_PATHS` и startup data layout. На этапе 3 исправление не вносилось.

### A-02. Composition root знает внутренности вкладок

`integrated_app.py` читает поля дочерних компонентов и вызывает их приватные методы напрямую. Это связывает UI-компоненты с деталями реализации соседних вкладок и затрудняет независимые изменения.

**Приоритет:** средний.  
**Рекомендация:** в будущем определить явные публичные методы/контракты для передачи плана, профиля, области и событий завершения; не переписывать сейчас без отдельного плана и тестов.

### A-03. Глобальное изменение sys.path и короткие имена импортов

Порядок импорта влияет на разрешение одинаковых коротких имён. Это подтверждено тестами для текущей конфигурации, но делает сборку и запуск чувствительными к изменениям путей.

**Приоритет:** средний/высокий для будущего рефакторинга.  
**Рекомендация:** сначала расширить диагностику импортов и portable smoke tests; переход к namespace-пакетам проводить отдельно и не удалять совместимые wrappers преждевременно.

### A-04. Tk callbacks из фонового потока и daemon lifecycle

Исполнитель передаёт UI-обновления через `root.after()`, вызванный из worker thread. Нормальный сценарий завершения предусмотрен, но закрытие окна в момент callback и аварийное завершение процесса требуют специальных проверок.

**Приоритет:** средний.  
**Рекомендация:** покрыть stop/close/error race tests и Windows integration test; не считать текущие unit tests доказательством thread-safety Tk.

### A-05. Синхронная обработка изображения в UI-потоке

Обработка, построение плана и quality analysis выполняются прямо из обработчиков Tk. На больших изображениях это может блокировать интерфейс.

**Приоритет:** низкий/средний до получения замеров.  
**Рекомендация:** сначала измерить задержки на репрезентативных изображениях; выносить операции в worker только вместе с контролем отмены и безопасным возвратом результата в Tk-поток.

## 3.11. Итог этапа

1. AutoDraw фактически является единым Tkinter-приложением с одним root/mainloop, а не двумя независимыми приложениями подготовки и исполнения.
2. `integrated_app.py` — composition root, управляющий импортами, путями, созданием вкладок и связями между ними.
3. Одноцветный и цветной сценарии сходятся в Stage 6, но сохраняют разные схемы плана, валидацию и контекст исполнения.
4. Общие геометрические модели и image-processing pipeline уже вынесены в отдельные shared-модули; compatibility wrappers продолжают обеспечивать прежние пути импорта.
5. Передача между UI в основном основана на прямом доступе к состоянию компонентов и callback-ах; runtime JSON используется как явная граница передачи плана.

## 4.3. Основные пользовательские сценарии

### Сценарий A. Одноцветное изображение

1. Пользователь выбирает файл изображения через диалог.
2. Изображение отображается в исходном preview; можно выделить прямоугольник crop мышью.
3. Размер холста может быть введён вручную, загружен из профиля либо синхронизирован с областью исполнителя.
4. Изменение параметров запускает обработку с debounce 180 мс; предыдущий отложенный callback отменяется.
5. На preview отображаются цветное подготовленное изображение, grayscale и бинарная маска.
6. Пользователь строит scanline-план с выбранным шагом строк.
7. Отдельно запускает quality analysis и получает Pixel Accuracy, Precision, Recall, F1, пропуски и лишние пиксели.
8. Проект `.autodraw` сохраняет исходник, бинарную маску, подготовленные изображения, план и метаданные. План также можно экспортировать как JSON для Stage 6.
9. Передача из вкладки 1 в executor проверяет наличие непустого плана; если quality analysis не запускался, показывает отдельное предупреждение. Затем план записывается во временный файл, повторно загружается как DrawingPlan, валидируется по границам и атомарно публикуется.

Важное предупреждение уже присутствует в UI: quality analysis оценивает DrawingPlan относительно бинарной маски, а не фактический след в игре. Это правильное разделение цифровой оценки и игрового результата.

### Сценарий B. Цветное изображение

1. Пользователь снимает/распознаёт палитру браузера или загружает существующий профиль.
2. Цвета можно исправить, подтвердить по одному/все, удалить; профиль сохраняется отдельно.
3. На вкладке 4 загружается изображение либо копируется prepared_color из вкладки 1.
4. До преобразования проверяется совпадение размеров изображения и целевой области; несовпадение блокирует действие.
5. Пользователь выбирает режим обработки белого фона и параметры оптимизации редких цветов/коротких сегментов.
6. После преобразования доступны preview, карта различий, таблица цветов и сохранение изображения/отчёта.
7. Вкладка 5 принимает результат только при совпадении порядка RGB-цветов в текущем профиле с палитрой, использованной при quantization. Несовпадение сбрасывает устаревший результат.
8. Строится scanline- или геометрический план; отображаются число штрихов/точек, видимые/прозрачные пиксели, переключения цвета, длина пути и оценка краски.
9. Передача в executor требует цветной план поддерживаемого типа и тот же профиль палитры, который использовался для создания плана.

Сильная сторона сценария: устаревшая карта цветов не применяется молча к изменённому профилю. Изменение целевой области также инвалидирует источник цветного плана.

### Сценарий C. Выбор области и исполнение

1. Область доски выбирается полноэкранным AreaSelector либо вводится координатами.
2. Координаты проверяются относительно текущего разрешения экрана и сохраняются в target profile.
3. Изменение области callback-ом синхронизирует размер холста вкладки 1 и целевой размер вкладки 4; цветной план вкладки 5 сбрасывается.
4. Перед запуском проверяются наличие плана/области, параметры ExecutorConfig, границы плана и текущий размер экрана.
5. Для цветного плана дополнительно проверяются точное совпадение размеров, профиль палитры и возможность построить целевые цвета. Для адаптивных кистей проверяется калибровка слайдера и отсутствие fallback-штрихов с неподтверждённой геометрией.
6. Пользователь подтверждает диалог с параметрами и предупреждениями; затем элементы управления блокируются, Stop становится доступным, запускается worker.
7. Во время исполнения обновляются состояние, прогресс и текущий штрих.
8. Stop/F12 запрашивает остановку; кнопка Stop блокируется, а исполнитель завершает cleanup и отпускает мышь.
9. По завершении формируется execution report, UI восстанавливает элементы управления и показывает результат. При закрытии окна во время исполнения пользователь может запросить остановку и отложенное закрытие до завершения.

Ограничение: подтверждение пользователя перед запуском обязательно для обычного UI пути; workflow callback для теста кисти пропускает стандартный второй диалог только после отдельного подтверждения фактического значения кисти.

### Сценарий D. Калибровка и тестирование кисти

Калибровка хранит отдельные точки, прямоугольные области, разрешение и режим выбора кисти. При смене разрешения координаты адаптируются/помечаются для повторной проверки; координаты со статусом `needs_review` блокируют соответствующие автоматические действия.

Тест кистей:
- предлагает набор шаблонов: горизонтальные/вертикальные линии, диагонали, короткие линии, прямоугольники, непрерывные повороты, замкнутые контуры, длинные изолированные линии, повторное покрытие, пересечения и серии для расхода;
- перед передачей плана проверяет профиль калибровки, разрешение экрана, наличие области и допустимость кисти;
- требует отдельный эталон пустой доски и подтверждение destructive Clear перед автоматической очисткой;
- перед запуском рисования требует ручного подтверждения фактического размера кисти в браузере;
- после исполнения может снять изображения до/после, измерить видимость штрихов, очистить доску и сравнить её с эталоном, проверить восстановление индикатора краски и вернуть кисть;
- сохраняет manifest эксперимента, execution report и импортированный Game Monitor report как отдельные артефакты.

Тест лимита краски отдельно требует подтверждения сопоставимого/полного запаса краски, блокирует передачу без этого флага и просит записать наблюдение после выполнения. Это снижает риск сравнения серий с разным исходным запасом, но само подтверждение остаётся ручным.

## 4.5. Проблемы интерфейса и сценариев

### UI-01. Синтаксическая ошибка блокирует создание всего интерфейса

В `source/preparation/brush_behavior_test_ui.py:141` в словаре `TEST_CASES` находится лишняя запятая после закрывающего элемента (`},,`). Это SyntaxError на этапе импорта.

`integrated_app.py` импортирует `BrushBehaviorTestTab` в общем блоке импортов при старте приложения. Поэтому ошибка не ограничивается вкладкой теста кистей: она блокирует импорт composition root и запуск всего приложения, включая обычную подготовку и исполнение.

Подтверждение CI на текущем HEAD: Windows portable build/startup smoke-test падает при импорте `integrated_app.py` с SyntaxError в строке 141. Это блокирующий дефект запуска. В рамках анализа исправление не вносилось.

### UI-02. Прокрутка вкладки калибровки привязана только к Canvas

`brush_calibration_ui.py:239–252` создаёт scrollable Canvas, но обработчик `<MouseWheel>` назначается самому Canvas. В отличие от вкладок подготовки, executor, теста кистей и теста лимита краски, рекурсивная привязка обработчика ко всем дочерним виджетам здесь не обнаружена.

В Tkinter событие колеса, возникшее над Entry/Button/Label, обычно обрабатывается bindtags самого дочернего виджета, а не произвольного родительского Canvas. Поэтому прокрутка при наведении на содержимое может не срабатывать; это статически выявленный риск, который следует подтвердить на Windows. Linux Button-4/Button-5 также явно не привязаны в этом обработчике.

**Рекомендация:** унифицировать binding колесика с другими прокручиваемыми вкладками и проверить прокрутку при наведении на каждую группу элементов.

### UI-03. Высокая плотность элементов управления в отдельных вкладках

Вкладка 5 содержит одновременно scanline, геометрический режим, параметры экспериментальной модели краски, оптимизации и таблицу результатов. Вкладка 8 содержит много отдельных точек/областей и калибровочных параметров. Прокрутка предусмотрена, но плотность и количество терминов увеличивают порог входа.

Это UX-наблюдение по структуре, а не подтверждённая проблема размеров/перекрытий. Требуется ручная проверка на минимальном поддерживаемом окне 1050 × 720 и на экранах с масштабированием Windows.

### UI-04. Вкладка 7 перегружена разными фазами одного эксперимента

В одной вкладке совмещены шаблоны, управление кистью, очистка, снимки, ручные измерения, импорт Monitor/Execution reports, manifest и сохранение записи. Workflow последователен, но UI должен одновременно объяснять подготовку, выполнение, сбор доказательств и восстановление состояния.

**Рекомендация:** не дробить вкладку автоматически; сначала проверить пользовательский сценарий по реальному прогону и определить, какие группы действий должны быть доступны на каждом состоянии эксперимента.

### UI-05. Crop preview не полностью согласует drag и release за границей

В `ImagePreview._on_drag()` текущая позиция визуально ограничивается прямоугольником изображения, но `_on_release()` заново вызывает преобразование фактической позиции указателя без такого ограничения. Если пользователь начинает выделение внутри изображения и отпускает кнопку за его границей, выделение может не примениться.

**Приоритет:** низкий.  
**Рекомендация:** проверить UX и, если воспроизводится, использовать последнюю ограниченную позицию при отпускании.

### UI-06. Разные модели прокрутки

В проекте одновременно используются:
- общий `ScrollableTabContent` с поддержкой вложенных виджетов и передачи прокрутки внутренним scrollable controls;
- собственные Canvas/Scrollbar в executor, quantizer, brush test, paint limit и calibration;
- упрощённые обработчики только на Canvas в calibration.

Это не само по себе дефект, но увеличивает риск разного поведения на Windows/Linux и при вложенных Treeview/Text/Canvas. Необходимо тестировать колесо, trackpad, Button-4/Button-5 и передачу прокрутки вложенным элементам.

## 5.1. Карта конвейеров

В проекте фактически существуют два отдельных конвейера подготовки.

### Одноцветный конвейер (Stage 13 workbench)

`source/preparation/stage13_workbench.py` использует общий модуль `shared_image_processing/pipeline.py`:

1. Загрузка исходника через `load_rgb_image()`: EXIF orientation применяется через Pillow `ImageOps.exif_transpose`; изображение приводится к RGB; прозрачность RGBA/LA сводится на белый фон.
2. Пользовательский crop в координатах исходного изображения.
3. Вписывание в целевой холст одним из режимов:
   - `contain` — сохранение пропорций, свободные области заполняются белым;
   - `cover` — сохранение пропорций с центральным crop после масштабирования;
   - `stretch` — независимое масштабирование по X/Y.
4. RGB → grayscale через OpenCV.
5. Необязательный median blur: уровни 1–4 дают kernel 3, 5, 7, 9.
6. Контраст/яркость с ограничением результата диапазоном 0–255.
7. Ручной threshold или Otsu.
8. Построение горизонтальных растровых штрихов с сохранением порядка строк и коротких сегментов.
9. Анализ качества относительно исходной бинарной маски.

Настройки `ProcessingSettings`: brightness -100…100, contrast 0.5…2.5, denoise 0…4, threshold 0…255. Размер холста ограничен 40 млн пикселей; crop должен быть внутри исходника и не меньше 2×2.

Результат `ProcessingResult` содержит три изображения одного размера: `prepared_color`, `grayscale`, `binary_mask`, а также применённый threshold, размеры, fit mode, crop и настройки. В бинарной маске чёрный означает тёмный foreground, белый — фон.

Путь кода: `shared_image_processing/pipeline.py`; совместимые import wrappers расположены в `source/preparation/image_processing/` и `source/executor/image_processing/`. Оба wrapper импортируют одни и те же классы/функции из общего модуля, а не содержат независимые реализации.

### Цветной конвейер (Stage 18 → Stage 19/20)

1. Входом служит подготовленное изображение и выбранный профиль браузерной палитры.
2. Фон либо сохраняется, либо обрабатывается одним из специальных режимов.
3. Видимые пиксели сопоставляются с ближайшим цветом фиксированной палитры.
4. Необязательное объединение редких цветов.
5. Необязательное объединение коротких горизонтальных цветовых сегментов.
6. Результат хранится как RGBA preview + двумерная `index_map`; индекс `-1` означает прозрачность.
7. Из карты строится цветной scanline-план или геометрический цветной план.
8. При необходимости план оптимизируется по бюджету и/или разбивается на несколько досок.

UI Stage 18 проверяет совпадение размеров исходного изображения с ожидаемой областью рисования. Сам quantizer не масштабирует изображение: он сохраняет входные ширину/высоту. Это отделяет нормализацию размеров от сопоставления с палитрой.

## 5.2. Палитра, квантование и фон

### Нормализация палитры

`palette_quantization.py`:
- принимает RGB или HEX, проверяет целочисленные компоненты 0…255 и согласованность RGB/HEX;
- отклоняет дубликаты RGB;
- ограничивает палитру 512 цветами;
- сохраняет исходный порядок палитры, назначая стабильные индексы.

Квантование выполняется по CIELAB + CIEDE2000. Каждый видимый пиксель сопоставляется с ближайшим цветом; прозрачные пиксели остаются прозрачными и получают индекс -1. Dithering отсутствует, геометрия и одиночные детали не размываются пространственной фильтрацией. Расчёт блоковый, с ограничением общего числа сравнений 300 млн и лимитом изображения 40 млн пикселей.

Отчёт содержит число изменённых пикселей, среднее/p95/p99/max ΔE00, число используемых/неиспользуемых цветов и распределение пикселей по палитре. Эти метрики характеризуют исходное ближайшее сопоставление; изменения после объединения редких цветов отражаются отдельно.

### Режимы удаления белого фона

UI предлагает взаимоисключающие режимы:
- `preserve` — белый остаётся обычным цветом;
- `edge` — удаляются только почти белые пиксели, связанные с краем изображения;
- `all_white` — удаляются все пиксели, сопоставленные с почти белыми цветами палитры;
- `auto_white_30` — удаление всех таких пикселей, только если доля белого строго больше 30%.

В режиме `edge` используется RGB-допуск по каждому каналу и 4-связность. Поэтому белые области внутри замкнутого контура сохраняются, если не соединены с краем через пиксели, попадающие в допуск. Это не «удалить все белые пиксели».

В режимах `all_white` и `auto_white_30` белый определяется по цветам палитры: каждый RGB-канал должен находиться не дальше заданного допуска от 255. Процент считается среди видимых пикселей после квантования и до удаления. Порог 30% строгий: ровно 30% не удаляется. После удаления пиксели получают alpha=0 и индекс -1, поэтому последующие планировщики их пропускают.

**Соответствие прежнему требованию:** логика «удалить белый, если его доля превышает 30%» реализована отдельным режимом `auto_white_30`; это не поведение по умолчанию. В режиме сохранения фона белый продолжает рисоваться. При необходимости удалить белый всегда следует использовать `all_white` или `edge` в зависимости от того, нужно ли сохранять внутренние белые детали.

### Сведение редких цветов и коротких сегментов

Реализованы два последовательных, различных алгоритма:

1. `merge_rare_palette_colors()`: редкий цвет определяется порогом количества пикселей ИЛИ долей; целевой цвет должен быть достаточно частым (по умолчанию не менее чем вдвое), а ΔE00 — не выше допустимого. Если близкого частого цвета нет, редкий цвет сохраняется.
2. `optimize_short_scanline_runs()`: рассматривает короткие горизонтальные участки. Учитывает соседние цвета, перцептуальную дистанцию ΔE00 и глобальную частоту; если слева и справа один цвет, это более сильное локальное свидетельство. Прозрачные пиксели не изменяются.

В UI обе оптимизации включены по умолчанию и выполняются после квантования/удаления фона: сначала редкие цвета, затем короткие сегменты. Это не один объединённый алгоритм, а два этапа с разными критериями. Их суммарное изменение карты цветов должно оцениваться по отчёту и preview; они способны уменьшать число цветовых переключений/штрихов ценой потери мелких цветных деталей.

## 5.3. Растровое построение цветного плана

`build_color_scanline_plan()` проходит строки сверху вниз, внутри строки — слева направо. Соседние пиксели объединяются только при совпадении точного индекса палитры. Прозрачность и смена цвета завершают текущий сегмент.

Параметры:
- `row_step_px` — шаг строк, минимум 1;
- `row_offset_px` — фаза выборки от 0 до row_step-1;
- `max_strokes` — максимум 250 000;
- бюджет и overhead для оценки ресурса;
- BoardItem type, лимит игровых точек и параметры point-quota estimate.

Отчёт разделяет:
- исходные видимые пиксели;
- нарисованные пиксели выбранных строк;
- пропущенные шагом строки пиксели;
- настоящие прозрачные пиксели;
- число штрихов, одиночных пикселей, переключений цвета, длину рисования и pen-up distance.

Шаг строк действительно прореживает рисунок, а не только меняет плотность preview. Это важная потеря данных, которая явно отражается в `omitted_by_row_step_pixel_count`. UI Stage 19/20 имеет собственный выбор шага 1, 2, 3, 4, 5, 8, 10; автоматическая подгонка может установить и другое значение.

**Одиночный пиксель:** scanline-план сохраняет его как нулевой по длине сегмент с двумя одинаковыми точками. Это сделано намеренно, чтобы не расширять штрих на этапе построения плана и не задеть соседний цвет. Preview Stage 20 и исполнительная интеграция предусматривают превращение такого singleton в короткое горизонтальное движение длиной 1 px (если справа остаётся место). Сам планировщик не превращает его в 2 px и не удаляет. Фактическая траектория мыши относится к этапу 6 и здесь не проверялась.

## 5.4. Геометрические цветные планы

`build_geometry_color_plan()` поддерживает три режима:

| Режим | Преобразование | Смысл и ограничения |
|---|---|---|
| `scanline` | Горизонтальные участки одного цвета | Сохраняет цветовую карту наиболее непосредственно; максимальное число мелких сегментов |
| `contour` | OpenCV contours для каждого цветового слоя | Рисует границы цветных областей, а не заполняет их автоматически |
| `skeleton` | Zhang–Suen thinning и трассировка графа | Превращает толстые цветовые области в центральные линии; не является заливкой |

Каждый цвет обрабатывается отдельной бинарной маской. Для contour/skeleton доступна фильтрация связных компонент по минимальной площади. Это может удалить небольшие островки и детали. В scanline-режиме фильтрация применяется только при явно заданном `min_component_area > 1`; значение по умолчанию 1 сохраняет пиксели.

Упрощение траекторий использует `cv2.approxPolyDP` (Ramer–Douglas–Peucker). После упрощения каждый сегмент проверяется растеризацией в ROI и должен оставаться внутри маски соответствующего цветового слоя. Это снижает риск срезать угол через соседний цвет/прозрачность, но не является доказательством совпадения с игровым рендером.

Скелетизация сохраняет изолированный одиночный пиксель: графовый tracer создаёт singleton-путь, а модель плана представляет его двумя одинаковыми точками. В contour-режиме одиночный компонент также сохраняется как `contour-point`. Это подтверждено тестами.

При `color_grouping=True` пути ориентируются и переупорядочиваются оптимизатором маршрута; исходный порядок строк больше не сохраняется. Поэтому уменьшение pen-up distance/переключений цвета может менять порядок рисования. Если порядок слоёв важен для конкретного изображения, нужно проверять выбранный режим и результат на preview.

**Критическое смысловое различие:** contour и skeleton — альтернативные геометрические интерпретации растровой цветовой маски, а не взаимозаменяемые способы сохранить исходную заливку. Геометрический план нельзя считать пиксельно эквивалентным цветной карте без проверки качества. Для заливки широкими кистями существует отдельный экспериментальный `interior_fill_planner`; его штрихи имеют `safe_to_execute: false` и не должны передаваться в автоматическое исполнение.

## 5.5. Бюджет, игровые точки и разбиение на доски

В проекте сосуществуют две модели ограничений, которые нельзя смешивать:

1. **Оценка расхода** — эмпирический pixel-equivalent: длина пути + дополнительный 1 px для singleton + overhead на каждый штрих. Значения по умолчанию: overhead 6.67 px-equivalent, бюджет 25 650 px-equivalent. Калибровка основана на четырёх измерениях. Это не универсальный физический объём краски и не отдельный запас для каждого цвета: игровая квота общая.
2. **Квота игровых точек** — отдельная оценка числа сохраняемых игровых координат с учётом шага, задержки, FPS, лимита BoardItem и safety factor. Геометрический оптимизатор принимает кандидата только при выполнении обоих ограничений.

Геометрический оптимизатор перебирает scale 1.0…0.05, наборы допусков RDP и минимальной площади компонента. Сначала ищет кандидатов, проходящих оба бюджета, затем выбирает лучший по точности видимых пикселей, общему числу несовпадений и другим tie-break критериям. Если ни один вариант не проходит, возвращает вариант с минимальным нормализованным давлением на бюджеты и выставляет признак необходимости multi-board split.

Оценка качества геометрического плана сравнивает программный preview с исходной index map и отдельно считает:
- общие несовпадения;
- точное совпадение видимых пикселей;
- непокрытые исходные пиксели;
- закрашивание исходной прозрачности;
- неверный цвет.

Это точное сравнение с программным preview, но не с фактическим браузерным следом. Оно не подтверждает поведение игры, реальную толщину кисти или расход ресурса.

Multi-board splitter делит векторные штрихи по пространственным прямоугольникам с clipping (Liang–Barsky), а не переразмечает отдельные штрихи произвольно. В манифесте сохраняются исходные tile bounds и дочерние планы. Для физических ограничений по умолчанию указаны 660×340, минимум tile 24 px и максимум 64 доски. Дочерние планы имеют полный размер холста доски, а их координаты локализованы к началу; метаданные tile нужны для последующей сборки общей картинки.

Параметры 660×340 в splitter и логический размер доски 420×240 из модели игрового движка относятся к разным слоям координат/представления и требуют отдельной сверки на этапах 6–7. Нельзя автоматически считать их одним размером.

## 5.6. Форматы планов и проверки

В проекте нет единого универсального формата плана для всех этапов:

- одноцветный `DrawingPlan`: `schema_version`, `coordinate_system=local_canvas_pixels`, `canvas`, summary и strokes; модель `Point`/`Stroke`/`DrawingPlan` находится в `geometry_models/`, старые пути — совместимые wrappers;
- цветной scanline: `autodraw_color_scanline_plan`, schema v1, palette, canvas, generation, summary, strokes;
- геометрический цветной: `autodraw_geometry_color_plan`, schema v1, palette, source, generation, summary, strokes;
- многодосочный манифест: `autodraw_multi_board_manifest`, schema v1, список tile и вложенных планов.

Цветные валидаторы проверяют тип/версию, размеры, целочисленную index map, диапазон индексов, соответствие цвета палитре, число штрихов, точки и порядок (для scanline), согласованность summary. Геометрический validator проверяет границы холста, корректность точек/closed, палитру и соответствие цвета индексу. Он не доказывает пиксельное покрытие — для этого есть отдельный quality report.

В `DrawingPlan.validate_bounds()` координаты допускаются в диапазоне включительно до width/height, тогда как цветной geometry validator требует `0 <= x < width` и `0 <= y < height`. Это различие контрактов координат нужно учитывать при унификации моделей и передаче планов между подсистемами; на данном этапе оно зафиксировано как риск, а не исправлялось.

Сохранение геометрического и цветного плана использует временный файл и атомарную замену после валидации. Одноцветный `DrawingPlan.save()` записывает JSON напрямую. Надёжность хранения и восстановление после сбоя подробнее рассматриваются на этапе 8.

# Этап 6. Исполнитель и взаимодействие с браузером

**Проверенный HEAD до записи:** `c846bccf8a1e03a01efacd6088aef2617bbfb4b4`

## 6.1. Карта исполнительного потока

Главная реализация — `source/executor/stage6_execute_plan.py`; низкоуровневый движок — `source/executor/drawing/mouse_executor.py`. Единый UI передаёт управление `Stage6App` через два маршрута:
- одноцветный DrawingPlan;
- цветной scanline/geometry plan, преобразуемый в DrawingPlan и исполняемый с обязательными цветовыми hooks.

В обоих случаях после загрузки выполняются проверка плана и построение preview. Кнопка запуска активна только при наличии плана и корректной целевой области. При запуске:
1. Читается и валидируется `ExecutorConfig`.
2. План повторно проверяется на bounds.
3. Экранная область перепроверяется относительно текущего разрешения.
4. Для цветного плана проверяются палитра, профиль и точное совпадение размера плана с областью.
5. Для adaptive-brush плана дополнительно валидируются исходный цветной план, калибровка slider и отсутствие fallback-штрихов без подтверждённой геометрической безопасности.
6. Настройки сохраняются, пользователю показывается подтверждение с параметрами/оценкой расхода (если запуск не пришёл из доверенного workflow).
7. UI блокирует повторный запуск и редактирование исполнительных параметров, создаёт worker thread.
8. Worker запускает MouseExecutor, который выполняет countdown, preflight, подготовительные клики, штрихи и cleanup.
9. Результат передаётся в Tk UI через `root.after`; создаётся execution report, восстанавливаются кнопки и показывается итоговый статус.

Подготовка и выполнение разделены: UI не двигает мышь самостоятельно. `MouseExecutor` не знает о Tk widgets и получает готовый `DrawingPlan`, абсолютное начало области, конфигурацию, Stop Event и необязательные callbacks.

## 6.2. Область доски и экранные координаты

`AreaSelector` открывает полноэкранное полупрозрачное окно, позволяет выделить прямоугольник мышью и отменить действие Esc. Минимум — 50×50 px. `TargetArea` хранит экранные X/Y и ширину/высоту.

При старте процесса `stage6_execute_plan.py` вызывает Windows `SetProcessDPIAware()` до импорта PyAutoGUI. Координаты области и PyAutoGUI предполагаются физическими пикселями. Выбранная область синхронизируется с workbench и цветным quantizer; изменение области инвалидирует цветной источник/план и требует повторной подготовки.

`validate_target_area()` проверяет целые координаты, неотрицательные X/Y, минимальный размер и попадание прямоугольника в текущий экран. Проверка повторяется перед каждым запуском, поэтому устаревший профиль не принимается автоматически после изменения разрешения.

Одноцветный план может быть преобразован в размер области:
- при сохранении пропорций — единый scale и центрирование;
- без сохранения пропорций — независимый scale X/Y.
Исходный план не изменяется; fit создаёт новый DrawingPlan и сохраняет параметры трансформации в `PlanFitInfo`.

Для цветного плана fit отключён. Размер должен совпадать точно, иначе Start блокируется. Это правильная защита от сдвига координат пиксельной карты и экранной палитры.

**Граница контракта координат:** модели плана допускают координату на правой/нижней границе (x == width, y == height), а экранная область описывается шириной/высотой и валидируется условием x + width <= screen_width. MouseExecutor переводит координату непосредственно в screen_x = area_x + point.x. При endpoint на крайней границе это может дать координату screen_width/screen_height, то есть на единицу за последний индекс экрана. Unit tests проверяют bounds плана и ограничение extension по холсту, но не реальный Windows cursor на последнем пикселе. Это требует отдельного физического теста; не утверждается, что на всех версиях PyAutoGUI это обязательно приводит к ошибке.

Текущая реализация селектора и валидации использует размер основного экрана PyAutoGUI и координаты от нуля. Отрицательные X/Y запрещены. Поддержка виртуального рабочего стола с мониторами слева/сверху от основного экрана, отрицательными координатами и независимым DPI не подтверждена.

## 6.3. Движение мыши и геометрия штрихов

`MouseExecutor` использует PyAutoGUI:
- `moveTo(..., duration=0)` для позиционирования и промежуточных точек;
- `mouseDown()` перед штрихом;
- `mouseUp()` после каждого штриха и в общей cleanup-секции.
- `pyautogui.PAUSE = 0`, `pyautogui.FAILSAFE = True`; встроенный FAILSAFE не отключается.

Отрезок делится на `ceil(distance / point_step_px)` шагов, каждый шаг интерполируется линейно. Стартовая точка устанавливается до mouseDown, а затем указатель проходит сегменты под удерживаемой кнопкой. Значение по умолчанию point_step — 2 px; диапазон — 0.5…20 px. Задержка между промежуточными точками — 10 ms по умолчанию (0…100 ms).

Валидируемые задержки:
- после mouseUp — 20 ms по умолчанию;
- перед mouseDown — 20 ms;
- после mouseDown — 40 ms;
- удержание в конце штриха — 50 ms;
- countdown — 5 секунд (1…30).

Для открытых штрихов последний сегмент может быть продлён на `line_extension_px` (по умолчанию 2 px, допустимо 0…20). Продление ограничивается локальными границами холста, не меняет исходный DrawingPlan и не применяется к закрытым контурам. Metadata штриха может переопределить extension; это используется геометрическими и adaptive-brush планами, где override равен 0.

Координаты округляются через `round()` при переводе в экранные целые координаты. Счётчик `move_calls` считает вызовы moveTo, включая установку стартовой точки и клики по палитре/slider; это не число игровых точек и не число пикселей рисунка.

## 6.4. Цветной исполнитель и browser palette

Цветной план не исполняется напрямую: `color_plan_to_drawing_plan()` сначала валидирует цветной документ и переводит его штрихи в общую модель. Метаданные сохраняют palette index, ID/название/HEX/RGB и исходный порядок.

До запуска `build_palette_targets()`:
- валидирует профиль;
- сравнивает разрешение профиля с текущим экраном;
- сопоставляет используемые цвета по точному RGB, а не только по индексу;
- требует, чтобы каждый реально используемый цвет имел статус confirmed/corrected;
- проверяет, что координаты swatch лежат в пределах сохранённого экрана.

После countdown `ColorPlanExecutionHooks.preflight()` делает свежий screenshot и сверяет профиль с изображением и текущим DPI scale Windows. Если статус не current, рисование не начинается. Это существенно снижает риск клика по устаревшей палитре, но не гарантирует, что браузер не изменит положение/состояние после снимка и до последующего клика.

Перед каждым штрихом `before_stroke()` выбирает swatch только если цвет отличается от уже выбранного. Затем вызывается mouseDown/mouseUp, и лишь после этого начинается рисование. Порядок исходных штрихов сохраняется; executor не группирует цвета и не переупорядочивает штрихи. При остановке между перемещением к swatch и кликом повторная проверка Stop не позволяет начать нажатие.

Цветные планы требуют обязательных hooks. Документация и код прямо указывают, что преобразованный DrawingPlan нельзя отправлять в обычный monochrome executor без этих hooks: в противном случае цветовые метаданные не приведут к выбору цвета.

## 6.5. Одиночные пиксели и extension

Для цветного scanline-плана singleton представлен двумя одинаковыми точками. При конвертации он превращается в горизонтальный drag длиной 1 px, чтобы игровое поле получило движение, а не click без перемещения. Для одиночного пикселя у правого края конечная точка может равняться width; это разрешено DrawingPlan.

Обнаружено существенное несоответствие preview и фактического исполнения:

- `color_plan_to_drawing_plan()` для scanline-плана добавляет metadata о singleton, но **не устанавливает** `line_extension_px_override=0`;
- стандартный `ExecutorConfig.line_extension_px` равен 2 px;
- MouseExecutor продлевает последний сегмент любого открытого штриха на эти 2 px;
- следовательно, scanline singleton, показанный в preview как 1 px drag, по умолчанию превращается в траекторию длиной до 3 px (с ограничением у края холста);
- соседний участок другого цвета может быть затронут. Аналогичный риск продления есть у обычных открытых цветных scanline-штрихов.

Для geometry color plan конвертер, напротив, всегда выставляет extension override 0: RDP пути уже проверены относительно маски своего цвета, и выход за неё запрещён. Для adaptive brush также принудительно используется extension 0.

Текущие тесты подтверждают конвертацию singleton в базовый 1 px drag, preview expansion и общую механику продления на 2 px. Однако интеграционный тест цветного scanline проверяет выбор цветов/порядок и наличие 1 px движения, но не проверяет, что фактический конечный endpoint singleton остаётся на +1 px. Поэтому именно взаимодействие singleton + default extension осталось непокрытым.

**Находка EXE-01 (высокий приоритет):** цветной scanline preview показывает базовый однопиксельный drag, тогда как стандартная настройка исполнения добавляет ещё 2 px. Это может нарушать границы цветовых участков и затирать соседние цвета. До исправления/отдельного теста безопаснее явно устанавливать extension 0 для scanline-плана или проводить исполнение с нулевым extension; код в рамках аудита не менялся.

## 6.6. Адаптивная кисть

Адаптивный план использует тот же цветной исполнитель и дополнительные metadata для выбора размера кисти перед штрихом. `BrushSliderCalibration` хранит точки slider, диапазон 1–30, начальное значение и разрешение экрана. Проверяется, что slider не пересекает область рисования и разрешение совпадает с калибровкой.

`BrushSliderController` перемещает бегунок мышью только при изменении значения, проверяет диапазон и Stop, освобождает кнопку через тот же cleanup. Adaptive plan:
- должен относиться к точному исходному color plan (проверяется hash);
- должен иметь геометрически подтверждённые штрихи;
- не допускает legacy fallback strokes;
- не может выходить за исходный цветовой участок/менять запрещённое направление или строку;
- принудительно отключает extension.

Если adaptive brush plan не прошёл валидацию, запуск блокируется; автоматического исполнения fallback-геометрии нет. Подробная оценка самой методики подбора кистей и достоверности её экспериментальных данных относится к этапу 7.

## 6.7. Остановка, ошибки и завершение

Остановка доступна:
- кнопкой Stop через общий `threading.Event`;
- глобальной клавишей F12 через `pynput.keyboard.GlobalHotKeys`;
- PyAutoGUI FAILSAFE (указатель в углу основного экрана).

Stop проверяется до штриха, между точками и в каждой прерываемой задержке. Ожидание выполняется через `Event.wait()`, поэтому countdown и паузы могут быть прерваны немедленно. Причина F12 имеет приоритет, если позже поступил ещё и stop-button/window-close.

Каждый штрих обёрнут в finally с mouseUp. После любого исхода выполняется дополнительная попытка mouseUp, затем останавливается F12 listener. Ошибка release переводит результат в failed и явно сообщает пользователю, что отпускание мыши не подтверждено. Закрытие приложения во время исполнения предлагает запросить остановку и отложить destroy до завершения worker.

Остаётся стандартный риск внешнего ввода: пользователь может перемещать мышь/переключать окно во время countdown или исполнения. Исполнитель не проверяет непрерывно, что активным остаётся нужное окно браузера. Цветной screenshot preflight проверяет палитру, но не фиксирует активное окно и не предотвращает последующий focus switch.

Worker вызывает `root.after()` для передачи прогресса/результата в Tk. Это распространённый мост из фонового потока, но вызов Tk API из worker thread остаётся чувствительной к состоянию Tcl/Tk операцией. Сквозной GUI stress-test при закрытии/остановке не найден; архитектурный риск из этапа 3 подтверждается на конкретном пути исполнения.

## 6.8. Отчёты и воспроизводимость исполнения

Каждый обычный запуск создаёт JSON report schema v2. Сохраняются:

### BoardPane и геометрия

- Логический размер доски: 420×240.
- `redraw()` вызывает `graphics.lineStyle(s, p, 1, false)`, где `s` берётся из `atom.radius[a]` напрямую. В этом пути значение не умножается на два.
- `setRadius(t)` записывает `t` в `atom.radius` текущего штриха.
- `onDrawStart()` преобразует текущую позицию Stage в локальные координаты и добавляет начальную точку.
- `onDrawing()` вызывается через `ENTER_FRAME`; пока лимит не исчерпан, координата курсора преобразуется в локальную, проверяется попадание в прямоугольник доски, затем точка добавляется и доска перерисовывается.

### Фактическая семантика игрового ресурса CHALK

Ключевое уточнение найдено в `BoardPane.updateLess()`:

1. Метод проходит по всем вложенным массивам `atom.points` и считает все сохранённые точки.
2. Вычисляет `less = max - pointCount`.
3. Создаёт `BlackBoardEvent.CHALK` со значением `percent = less / max`.
4. UI устанавливает ширину `levelProgress` как `120 * percent`.

Следовательно, в просмотренной реализации индикатор CHALK отражает **остаток квоты игровых точек**, а не измеренный объём краски, площадь окрашивания или длину траектории. Внутренние `max`, `less` и количество точек являются более прямым источником, чем анализ пикселей индикатора на скриншоте.

`updateLess()` вызывается при начале штриха и после каждой принятой точки во время `ENTER_FRAME`. Поэтому число расходуемых единиц зависит от количества уникальных координат, принятых игровым циклом. Оно зависит от частоты кадров и скорости перемещения указателя: при одинаковой длине медленный проход потенциально может дать больше точек, чем быстрый. Длина пути не задаёт число точек однозначно. В просмотренном коде `setRadius()` меняет радиус, но сам расчёт `less` не использует радиус; прямой зависимости квоты от размера кисти в этом механизме не видно.

Для расширенного режима `_isPainterExtend` метод `clear()` добавляет специальную начальную точку в первый массив и затем создаёт следующий пустой массив. Если исследуемый экземпляр использует этот режим, абсолютный `pointCount` может включать служебную точку. Для сравнений нужно фиксировать baseline до рисования и анализировать дельту, не трактуя абсолютное значение как количество пользовательских точек.

**Вывод:** число точек — непосредственная единица расхода CHALK-квоты в этом клиентском механизме. Это не доказывает, что все серверные ограничения/сохранение рисунка исчерпываются этим счётчиком. Нельзя называть этот показатель «расходом краски на пиксель» или выводить его из длины пути.

- Учитывает, что `onDrawing` мог быть зарегистрирован как обработчик `ENTER_FRAME` до замены метода; поэтому использует отдельный polling.
- Записывает `POINT_QUOTA_UPDATE`, `DRAW_SAMPLE`, события указателя, ошибки и Resource Timing.
- Ограничивает буфер 50 000 событиями; последующие события увеличивают `droppedEvents`.

### Обнаруженные ограничения и риски

**MON-01 — дополнительная стоимость полного обхода точек (высокий приоритет проверки).**  
`boardSnapshot()` вызывает полный рекурсивный подсчёт `atom.points`. В обёртке `updateLess` Monitor делает snapshot до оригинального метода, после него и ещё один snapshot внутри `emit()`. Сам оригинальный игровой `updateLess()` тоже полностью пересчитывает точки. Кроме того, 25-мс polling вызывает snapshot, после чего `emit()` снова создаёт snapshot. Таким образом, на растущей доске добавляются несколько O(N) обходов поверх уже существующего игрового O(N) обхода. Это доказанная структура вычислений, но величина влияния на FPS пока не измерена.

**MON-02 — Monitor не экспортирует прямые поля счётчика CHALK.**  
`boardSnapshot()` включает `pointCount` и `radius`, но не включает `board.max` и `board.less`. Событие `POINT_QUOTA_UPDATE` содержит snapshot и аргументы, но не прямые значения остатка/максимума. Поэтому Monitor позволяет наблюдать число точек, однако его текущий публичный `status()/export()` не даёт точного снимка CHALK без дополнительного чтения полей игры. Код не менялся; это зафиксированный разрыв между доступными данными движка и экспортом Monitor.

**MON-03 — возможная потеря strokeId в событии конца.**  
`pointerup` listener установлен на `window` в capture-фазе и сбрасывает `activeStrokeId`. Если Egret после этого обрабатывает тот же pointer-up и вызывает `onDrawEnd/onDrawingEnd`, соответствующий `DRAW_END` будет создан уже без исходного ID. Это следует из порядка обработчиков в коде, но точная последовательность в целевом Firefox/Egret требует живого smoke test. События `POINTER_UP_CANDIDATE` и финальный sample могут быть сохранены раньше сброса.

**MON-04 — восстановление методов не доказано тестом.**  
`detach()` восстанавливает исходный собственный descriptor либо удаляет временное own-свойство, если метод был унаследован. Ошибки восстановления добавляются в `errors`, но автоматической сверки всех ссылок/descriptors до attach и после stop в просмотренном модуле нет. Нужны проверки attach → stop, повторный start/stop, смена BoardPane и частичный отказ установки wrapper.

**MON-05 — экспорт не самодостаточен для воспроизведения.**  
В export есть версия Monitor, performance-relative timestamps, URL/frame context, события и счётчики буфера. Сам экспорт не содержит идентификатор эксперимента AutoDraw, SHA-256 игрового bundle, браузер/версию, viewport/DPI/zoom, калибровочный профиль и wall-clock anchor для перевода performance time в UTC. Эти сведения должны приходить из манифеста/интеграции, но автоматической привязки пока нет.

**MON-06 — сетевые события могут быть шире одного эксперимента.**  
`PerformanceObserver.observe({type:"resource", buffered:true})` может передать ранее буферизованные ресурсы страницы. Поэтому `NETWORK_RESOURCE` не следует автоматически считать запросом текущего штриха. Функция `safeUrl()` маскирует значения некоторых query-параметров по имени, но не гарантирует удаление секретов, встроенных в path или параметры с неизвестными именами. Не использовать этот поток как полный сетевой аудит.

**MON-07 — CI не проверяет поведение Game Monitor.**  
В `.github/workflows/geometry-tests.yml` для `game_monitor.js` выполняется только `node --check`. Отдельные unit/integration tests относятся к Python WebSocket smoke server; тестов JavaScript attach/detach, event ordering, point counting, export и overhead в найденном наборе нет. Успешный JS syntax check не подтверждает корректность жизненного цикла Monitor.


**MON-08 — повторный start без clear смешивает сессии.**  
`start()` обновляет `startedAt`, но не очищает `events`, `droppedEvents` и `errors`. Очистка выполняется отдельным `clear()`. Поэтому сценарий stop → start без clear оставляет события предыдущего запуска в следующем export, тогда как `startedAtPerformanceMs` уже относится к новому запуску. Это требует явной границы сессии при интерпретации JSON; ручной порядок status/download/clear из README предотвращает смешивание только при точном соблюдении процедуры.


## 7.3. WebSocket smoke server и границы bridge

Проверены `source/game_monitor/websocket_smoke_server.py` и `tests/test_websocket_smoke_server.py`.

Подтверждено в коде:
- bind только на `127.0.0.1`;
- HTTPS Origin allowlist задаётся явно и применяется в WebSocket handshake;
- одноразовый token генерируется через `secrets.token_urlsafe(32)`, сравнение выполняется через `hmac.compare_digest`;
- принимаются только две точные схемы: `auth` и `ping`;
- ограничение сообщения 1024 байта, ограничение nonce 64 символами;
- таймауты ожидания сообщений — 5 секунд;
- сервер не получает доступ к Game Monitor API, не принимает произвольные имена методов, не управляет игрой и не управляет мышью.

Тесты проверяют parser, одноразовость token, Origin rejection, отказ неверной авторизации и ping/pong. Это unit/integration-проверка транспортной оснастки, а не доказательство доступности loopback WebSocket из HTTPS iframe в Firefox.

Production bridge с запросами `status()/export()`, session/run ID, sequence, файловым сохранением и manifest persistence не реализован. Вопросы mixed content, Local Network Access/permission prompts и реального Origin игрового iframe остаются непроверенными. Статус Firefox browser smoke test — `not_tested`.

### Короткие штрихи: сопоставление executor и игрового sampling (2026-10-31)

В `mouse_executor.py` число перемещений сегмента равно `max(1, ceil(distance / point_step_px))`. При `point_step_px=2` длины 0/1/2/3/5/8/10 px создают 1/1/1/2/3/4/5 перемещений. Плюс семь стартовых `moveTo` дают 24 вызова — ровно значение manifest. Настройки: задержка точки 10 ms, ожидание после mouse-down 40 ms, удержание в конце 50 ms.

Нулевой отрезок вызывает перемещение в ту же координату; `BlackBoardAtom.pushPoint()` отбрасывает повторную точку, так что второй уникальной точки не появляется. Для 1 px координата меняется, но отдельный след на PNG не подтверждён, а Monitor в этой серии отсутствует. Игровой `onDrawing` опрашивает позицию через `ENTER_FRAME` (цикл около 30 FPS); число вызовов executor не равно числу игровых точек.

Итог: 7/7 completed strokes — только статус executor; 24 move_calls — команды перемещения. PointCount игры для этих запусков неизвестен. Нулевой отрезок не создаёт второй уникальной точки; регистрация 1 px не установлена.


Уточнение от 31.10.2026: логическая доска игрового движка имеет размер 420×240. Фактический экранный ROI больше из-за масштаба отображения; это разные системы координат. Автоматический исполнитель обязан преобразовывать логические координаты в экранные с учётом калиброванных положения и масштаба доски.
