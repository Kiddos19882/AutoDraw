## 4. Точные дубли — наивысший приоритет

По SHA в Git обнаружены следующие точные совпадения файлов. Это сильное основание для консолидации, но удалять копию можно только после унификации импортов.

### 4.1. Модели продублированы в двух пакетах

Точное совпадение содержимого:

- `source/preparation/models/point.py` и `source/executor/models/point.py`
- `source/preparation/models/stroke.py` и `source/executor/models/stroke.py`
- `source/preparation/models/drawing_plan.py` и `source/executor/models/drawing_plan.py`

**Риск:** идентичные классы, импортированные через разные имена модулей, могут стать разными Python-типами во время исполнения. Это особенно опасно, когда приложение добавляет обе папки в `sys.path`, а код использует короткий импорт `from models import DrawingPlan`. Результат может зависеть от порядка путей и способа запуска (обычный Python против frozen/portable).

**Рекомендация:** создать один канонический пакет общих моделей, например `source/common/models/`, и импортировать `Point`, `Stroke`, `DrawingPlan` из него в подготовке и исполнителе. Перенос делать отдельным коммитом:
1. Добавить канонический пакет и тесты сериализации.
2. Перевести импорты в подготовке и исполнителе.
3. Проверить round-trip JSON и совместимость старых планов.
4. Проверить порядок импорта в обычном запуске и portable-сборке.
5. Удалить старые копии только после поиска импортов и успешного CI.

Не следует просто удалять один из каталогов `models`: старые импорты могут быть частью отдельных сценариев и упаковки.

### 4.2. Pipeline обработки изображений полностью продублирован

Точное совпадение:

- `source/preparation/image_processing/pipeline.py`
- `source/executor/image_processing/pipeline.py`

Совпадает и `image_processing/__init__.py` в обоих каталогах.

**Рекомендация:** вынести реализацию в общий модуль и оставить при необходимости тонкие compatibility-обёртки с прежними импортами. Сначала проверить, не расходятся ли ожидаемые настройки подготовки и исполнителя: общая реализация допустима, если семантика одна и та же. Тесты должны проверять EXIF, прозрачность, contain/cover/stretch, crop box, порог и размер результата.

### 4.3. Повторяющиеся BAT-файлы

Точное совпадение:

- `source/preparation/run_tests.bat`
- `source/executor/run_tests.bat`

**Рекомендация:** оставить один корневой `run_tests.bat`/Python runner, а локальные BAT-файлы либо удалить после проверки внешних инструкций, либо сделать тонкими прокси, вызывающими общий `run_all_tests.py`. Сейчас уже есть общий тест-раннер, поэтому дублирующиеся команды создают лишние точки входа.

## 5. Кандидаты на удаление или перенос из Git

Здесь важно различать **точно лишние дубли**, **сгенерированные файлы** и **ценные исторические доказательства**.

### 5.1. Runtime-состояние в репозитории — кандидат на исключение

Путь: `AutoDraw_Stage20/data/runtime/current_brush_behavior_test.json`.

В текущем дереве его SHA совпадает с одним из сохранённых JSON-планов теста кисти. По имени это файл текущего runtime-состояния, а не эталонный источник. Runtime-файл не должен обновляться пользовательским запуском и попадать в обычные коммиты.

**Действие:** проверить, как приложение читает и создаёт этот файл; если он генерируется автоматически, добавить `data/runtime/` в `.gitignore`, оставить создание файла при запуске и удалить только отслеживаемый runtime-артефакт из Git. Не удалять файл из пользовательской рабочей папки без необходимости.

### 5.2. Повторяющиеся пустые снимки холста и индикатора краски

В экспериментальных папках много PNG с одинаковыми Git blob SHA:
- `blank-board-reference.png` совпадает с множеством `before_clear-board.png` и `after_clear-board.png`;
- одинаковые `before_clear-paint-meter.png` и `after_clear-paint-meter.png` повторяются в разных экспериментах;
- часть `after_draw-paint-meter.png` также совпадает между экспериментами.

Это реальное дублирование байтов, но JSON каждого эксперимента может ссылаться на конкретный путь. Поэтому **нельзя просто удалить PNG** — это сломает анализаторы, проверку результатов и воспроизводимость.

**Рекомендация:** ввести общий каталог эталонных снимков и ссылку/идентификатор в манифесте эксперимента. Обновить анализаторы на чтение общего эталона, затем убрать дубли из экспериментальных каталогов. Сначала выполнить миграцию и прогнать анализ всей серии; только после этого сокращать файлы. Если простой ссылки в JSON недостаточно для совместимости, хранить небольшой локальный копируемый snapshot для самостоятельного архива эксперимента.

### 5.3. Большие скриншоты экспериментов

В `data/results/brush_behavior_tests/` хранится около 300 PNG, включая полноэкранные снимки порядка 650–700 KB каждый. Эти изображения важны для измерений, но в Git они делают изменения и clone тяжелее, особенно если результаты повторно генерируются.

**Рекомендация:**
- в Git оставить эталонный минимальный набор, нужный unit/regression-тестам;
- для CI сохранять полные экспериментальные архивы как Actions artifacts;
- ручные измерения, которые нужно сохранить надолго, оставлять в отдельном архиве с манифестом, датой, конфигурацией и статусом доверия;
- не переносить единственные исходные доказательства без проверки, что архив доступен и анализатор умеет его читать.

Для уже проведённых измерений не рекомендуется массовое удаление только на основании статуса `legacy_unverified`: эти данные всё равно объясняют, почему калибровка не считается подтверждённой.

## 7. Архитектурный рефакторинг по подсистемам

### P0 — убрать неоднозначность импортов

Текущий `integrated_app.py` добавляет в `sys.path` две папки `source/preparation` и `source/executor`, а затем импортирует модули короткими именами (`models`, `stage8_optimizer`, `stage6_execute_plan`, `palette_quantization_ui`). При одинаковых именах пакетов и модулей это создаёт зависимость от порядка `sys.path`.

**Предлагаемая цель:**
- использовать единый пакетный namespace, например `autodraw.preparation`, `autodraw.executor`, `autodraw.common`;
- перейти на абсолютные импорты внутри пакетов;
- отказаться от добавления нескольких директорий в `sys.path` как механизма разрешения конфликтов;
- собирать portable-приложение через явный список пакетов/ресурсов;
- добавить тест, который импортирует ключевые классы в чистом процессе и проверяет их `__module__`/идентичность.

Это самый важный рефакторинг, потому что он уменьшает риск разных типов `DrawingPlan`, скрытых циклических зависимостей и различий между запуском из исходников и упаковкой.

### P1 — вынести бизнес-логику из UI

Tkinter-модули должны координировать виджеты и события, но не содержать весь алгоритм, IO и анализ.

Рекомендуемое разделение:
- UI: ввод параметров, отображение статуса, preview и события;
- сервисы: преобразование карты цветов, построение кандидатов, бюджетный поиск;
- репозитории/хранилища: чтение/запись JSON, профилей и экспериментов;
- отчёты: метрики качества/ресурсов и сериализация результата.

Начинать с `brush_behavior_test_ui.py` и `stage6_execute_plan.py`, потому что они наиболее крупные и связывают много действий. Делать небольшими этапами, с неизменным поведением и тестами на публичные методы. Не переписывать UI целиком параллельно с оптимизатором геометрии.

### P1 — общий контракт плана

Сейчас в проекте есть несколько форматов: геометрический цветной план, scanline-план, адаптивный brush plan и исполнительный `DrawingPlan`. Они имеют разные потребности, но требуют единого явного контракта передачи.

Рекомендуется:
- определить версионированную модель `DrawingPlan` и формат цветных штрихов;
- включать canvas dimensions, coordinate system, palette/profile reference, source hash, algorithm/version, safety status и ресурсные оценки;
- иметь явные адаптеры между scanline/geometry/adaptive plan и executor;
- валидировать границы, прозрачность, цвета и происхождение перед записью и перед исполнением;
- сохранять обратную совместимость для старых JSON через миграторы/версии схемы.

Не надо сводить все планы к одной модели до определения полей, которые реально нужны каждому режиму.

### P1 — объединить ресурсные оценки

Есть связанные компоненты: `board_resource_model.py`, `paint_cost_model.py`, `game_point_calibration.py`, `engine_point_calibration.py`, `interval_quota_fit.py`, `multi_board_splitter.py`, `geometry_budget_optimizer.py`, `paint_budget_optimizer.py`.

Не удалять их по сходству названий: они моделируют разные ограничения и этапы. Но нужно ввести общий объект отчёта кандидата:
- paint estimate + источник/версия модели;
- game point estimate + источник/версия модели;
- число штрихов, длина пути и оценка времени;
- покрытие и качество preview;
- `fits_paint_budget`, `fits_point_budget`, `fits_both`;
- safety/validation status.

Потом проверить, какие функции являются дублирующими, и только после тестов объединять. Удаление одного из двух оптимизаторов без переноса его проверенных правил опасно.

### P2 — привести палитру к слоям

В палитровом контуре есть `palette_detection.py`, `palette_profiles.py`, `profile_manager.py`, `palette_quantization.py`, `palette_reduction.py`, `palette_quantization_ui.py`, `palette_detection_ui.py`.

Предлагаемая граница:
- обнаружение цветов браузера;
- хранение/версионирование профиля палитры;
- квантование в палитру;
- уменьшение редких цветов и коротких сегментов;
- UI/preview.

Не объединять все эти файлы в один «palette.py»: это увеличит связность. Сначала убрать дублирующиеся функции и общий код преобразования/сериализации, если подтверждено тестами.

### P2 — отделить экспериментальный код

Бенчмарки, генераторы синтетических карт и анализаторы полезны, но должны быть явно отделены от runtime:
- runtime-модули не должны импортировать скрипты из `tests/`;
- тестовые инструменты не должны запускаться при импорте приложения;
- у каждого скрипта должен быть короткий docstring: входные файлы, результат, можно ли запускать автоматически;
- у генераторов/анализаторов должны быть тесты формата отчёта, но не обязательно тесты каждого CLI-флага.

## 8. Тесты и сборка

### Сохранить

- `run_all_tests.py` — единая точка запуска тестовых наборов.
- `smoke_test_portable.py` — проверка старта собранной версии.

1. Добавить тесты на неоднозначные импорты и совпадение общих моделей.
2. Проверить, что тест-раннер запускает все suites и корректно возвращает код ошибки.
