# Архитектура AutoDraw

**Версия приложения в исходниках:** 1.8.3  
**Основной файл приложения:** `integrated_app.py`

## 1. Назначение приложения

AutoDraw — настольное приложение для Windows, объединяющее подготовку изображения, работу с палитрами, создание планов рисования, вспомогательные операции с кистями и исполнение подготовленного плана на экранной области.

Приложение построено на Python и Tkinter. В репозитории также присутствуют JavaScript-инструмент Game Monitor, отдельный локальный WebSocket smoke server, тесты, данные лаборатории, сценарии сборки и CI workflows.

## 2. Верхнеуровневая схема

```text
AutoDraw_Stage20/
├── integrated_app.py          # единое Tkinter-приложение
├── launcher.py                 # отдельная точка запуска/совместимости
├── shared_image_processing/    # общий слой обработки изображений
├── geometry_models/            # модели геометрических данных
├── source/
│   ├── preparation/            # подготовка изображения и построение планов
│   ├── executor/               # экранная область и исполнение планов
│   └── game_monitor/            # браузерная диагностическая оснастка
├── data/                       # пользовательские профили и результаты
├── tests/                      # интеграционные и вспомогательные тесты
├── testOnWin/                  # данные калибровочных запусков Windows
└── testImages/                 # входные изображения для тестов и примеров
```

## 3. Слои приложения

### 3.1. Объединённый интерфейс

Файл `integrated_app.py` является основной точкой сборки интерфейса. Он создаёт главное окно Tkinter и вкладки приложения, подключает UI-компоненты подсистем подготовки, палитры, цветного плана, тестирования лимита, тестирования кистей и калибровки. В нём также задаются общие каталоги данных и пути импорта двух основных подсистем.

Файл `launcher.py` следует рассматривать как отдельную точку входа/запуска; точный способ его применения определяется его текущим содержимым.

### 3.2. Подготовка (`source/preparation/`)

Подсистема подготовки содержит UI и модули предметных областей:

- подготовка изображения и рабочее пространство;
- сегментация и преобразование изображения;
- обнаружение, хранение и применение профилей палитры;
- построение цветных планов;
- модели квот и оценок ресурсов;
- планирование кистей и геометрии;
- калибровочные и лабораторные сценарии.

Внутренние подпапки:
- `image_processing/` — компоненты обработки изображения;
- `models/` — модели планов, точек и штрихов;
- `tests/` — тесты подсистемы подготовки.

### 3.3. Исполнение (`source/executor/`)

Подсистема исполнения содержит компоненты экранного взаимодействия и обработки планов:

- `stage1_calibration.py` … `stage6_execute_plan.py` — файлы этапов/экранов исполнительной подсистемы;
- `drawing/` — исполнение цветных планов, преобразования планов и диагностические структуры;
- `image_processing/` — подготовка входных данных исполнительной подсистемы;
- `path_planning/` — компоненты планирования траекторий;
- `models/` — модели DrawingPlan, Point и Stroke;
- `tests/` — тесты executor.

### 3.4. Общие модели и обработка

- `geometry_models/` содержит общие геометрические модели.
- `shared_image_processing/` содержит общий конвейер обработки изображений.
- `source/preparation/models/` и `source/executor/models/` содержат модели, используемые соответствующими подсистемами.

При описании или изменении моделей необходимо отдельно фиксировать, какая подсистема импортирует соответствующий класс и какой формат данных передаётся между подсистемами.

### 3.5. Game Monitor

`source/game_monitor/` содержит браузерный JavaScript-snippet, README, экспортированные JSON-файлы состояния/событий и локальный WebSocket smoke server с отдельными зависимостями. Это вспомогательная диагностическая часть репозитория, а не основной интерфейс AutoDraw.

## 4. Основной пользовательский контур интерфейса

Состав вкладок единого окна определяется подключением в `integrated_app.py`:

1. Подготовка изображения.
2. Исполнение рисунка.
3. Палитра браузера.
4. Преобразование в палитру.
5. Цветной scanline-план.
6. Тест лимита краски.
7. Тест кистей.
8. Калибровка теста.

Передача подготовленных планов между вкладками реализована на уровне объединяющего приложения. Для документации форматов и мест хранения см. [CONFIGURATION_AND_DATA.md](CONFIGURATION_AND_DATA.md).

## 5. Зависимости между подсистемами

На уровне структуры репозитория выделяются следующие связи:

- `integrated_app.py` подключает UI-классы из `source/preparation/` и `source/executor/`.
- Подсистемы используют собственные каталоги `models`, `image_processing` и `tests`.
- Общие каталоги `data/` используются для профилей, палитр, проектов, результатов, калибровок и runtime-данных.
- `build_windows.py` и `build_windows.bat` относятся к упаковке единого приложения.
- `.github/workflows/` содержит автоматизированные проверки и вспомогательные измерительные workflow.

Это структурная карта импортов и размещения файлов, а не описание внутреннего выполнения алгоритмов.
