## 1. Условия эксперимента

Во всех 18 опытах использовались:
- радиус кисти: 10;
- `point_step_px=2`;
- `point_delay_ms=10`;
- `line_extension_px=0`;

- `after_mouse_up_ms=20`, `end_hold_ms=50`;

G2 содержит шесть сценариев по три независимых повтора: `continuous_closed_contour`, `continuous_turns`, `long_isolated_lines`, `parallel_spacing`, `cross_section_intersections`, `repeated_coverage`.

## 2. Приёмка качества данных

Проверены все 18 каталогов экспериментов и соответствующие Game Monitor captures:
- все 18 задач имеют статус `completed`;
- все 18 captures сохранены, `chalk.status=exact`;
- во всех опытах `post_point_count - pre_point_count = consumed_points`;
- сумма `DRAW_SAMPLE.pointDelta` совпадает с точным CHALK;
- фактический `stroke_count` совпадает с ожидаемым числом штрихов;
- радиус во всех captures единственный и равен 10;
- `dropped_events=0`, `monitor_dropped_events=0`, `monitor_error_count=0`;
- frame probe измерен во всех опытах.

Таким образом, G2 принят по критериям качества первичных данных. Точные значения CHALK берутся из игрового pointCount, а не из визуальной оценки полосы краски.

## 4. Отдельный результат повторного покрытия

Сценарий содержит три прохода по одной и той же горизонтальной траектории длиной 200 логических px и один контрольный параллельный проход такой же длины.

Агрегация `DRAW_SAMPLE.pointDelta` по четырём stroke ID:

| Повтор | Повторный проход 1 | Повторный проход 2 | Повторный проход 3 | Контрольный проход | Всего |
|---|---:|---:|---:|---:|---:|
| 1 | 61 | 62 | 62 | 62 | 247 |
| 2 | 61 | 61 | 61 | 62 | 245 |
| 3 | 61 | 61 | 62 | 62 | 246 |

Каждый повторный проход по уже использованным координатам снова расходует примерно 61–62 CHALK. Это близко к контрольному проходу по новой параллельной траектории. В рамках данного сценария повторное рисование поверх существующей линии **не даёт заметной экономии CHALK**.

Это важный результат для планировщика: геометрическое перекрытие нельзя считать бесплатным только потому, что визуально линия уже нарисована. Вывод относится к проверенной траектории, радиусу 10 и текущим параметрам executor; он не доказывает одинаковое поведение для любых типов наложения.

## 5. Сопоставление сценариев и ограничения

Средний расход шести сценариев находится в диапазоне 212–444,67 CHALK. Различия между сценариями в первую очередь связаны с общей геометрией и количеством пройденных линий; сами средние нельзя сравнивать как изолированную «стоимость поворота» или «стоимость пересечения» без нормализации на длину и точную конфигурацию.

В Game Monitor поле `trajectory.status` остаётся `incomplete_until_verified`: coalesced `pointDelta` может скрывать промежуточные принятые координаты. Поэтому `observed_segment_length_lower_bound` — нижняя граница наблюдаемой траектории, а не доказанная полная длина. Отношения CHALK к этой величине не следует превращать в production-формулу.

Что G2 подтверждает:
1. повороты, замыкание контуров, пересечения и близкое расположение линий не вызывают ошибок capture и корректно учитываются в общем точном CHALK;
2. повторный проход по той же линии расходует почти столько же CHALK, сколько контрольный проход по новой линии;
3. при фиксированных радиусе и параметрах executor повторяемость сценарных результатов высокая: внутри каждого сценария диапазон составляет 1–3 CHALK.

Что G2 не подтверждает:
- универсальную формулу расхода для любой геометрии;
- влияние радиуса кисти (для этого нужна отдельная матрица радиусов);
- влияние `point_step_px` и `point_delay_ms` (это задача G3);
- точное восстановление всех промежуточных координат траектории из coalesced telemetry;
- визуальное качество покрытия или эквивалентность повторного прохода с точки зрения изображения.

## 6. Решение по этапам

- **G1: принят.**
- **G2: принят**, 18/18 задач, первичные captures прошли проверки.
- **G3: разблокирован.**

Следующий этап — G3: контрольная геометрия `paint_consumption_long_lines`, радиус 10, шесть линий; матрица `point_step_px = 1, 2, 4` × `point_delay_ms = 5, 10, 20`, три повтора на комбинацию, всего 27 независимых опытов. Между комбинациями менять только эти два параметра. Сохранять отдельные baseline/captures, рандомизированный порядок и safety stop на 80%.

G3 должен отдельно показать, как sampling step и delay влияют на точный CHALK, число move calls, длительность, FPS и потери событий. Не приравнивать move calls к расходу CHALK. Production-модель не считать валидированной до независимой проверки на контрольных рисунках.


## 7. Готовность реализации G3 (важное уточнение)

Принятие G2 открывает исследовательский gate G3, но не означает, что G3 уже можно запускать из текущего UI. Проверка кода на HEAD после фиксации G2 показала:
- `PHASE_SCENARIOS` в `source/preparation/chalk_experiment_matrix.py` содержит только G1 и G2;
- `BLOCK_PHASES` в `source/preparation/chalk_test_blocks.py` поэтому также ограничен G1/G2;
- UI `brush_behavior_test_ui.py` предлагает только G1/G2 и явно проверяет только эти фазы;
- текущие validation/identity rules рассчитаны на G1/G2 и фиксированный executor config.

Перед первым live G3 требуется реализовать G3 в matrix metadata, block plan/journal validation, UI и analyzer. G3 должен идентифицировать ячейку по комбинации `point_step_px`, `point_delay_ms` и `repeat_index`, чтобы девять комбинаций с тремя повторами не конфликтовали как дубликаты одного сценария. После реализации обязательны regression tests, полный CI и Windows portable startup smoke-test. До этого G3 считается **разблокированным по результатам G2, но не готовым к live-запуску**. Геометрию, матрицу 27 опытов и фиксированные условия G3 менять не нужно.
