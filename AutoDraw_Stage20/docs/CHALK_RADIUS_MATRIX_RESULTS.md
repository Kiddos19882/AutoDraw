# Результаты матрицы расхода CHALK по радиусам кисти

**Серия:** `chalk-20261101-023127-b85dbb`  
**Коммит с первичными данными:** [e2af4d0a69e2bd89b610b58678e20e86475cb8d0](https://github.com/Kiddos19882/AutoDraw/commit/e2af4d0a69e2bd89b610b58678e20e86475cb8d0)  
**Сценарий:** `paint_consumption_long_lines`  
**Статус:** 21/21 матричных экспериментов приняты по критериям exact capture.

## 1. Условия измерения

- Доска: 460×240 логических px.
- Шесть отдельных горизонтальных штрихов от X=20 до X=420.
- Длина одного центрального пути: 400 px; суммарно: 2400 px.
- Одинаковые план, координаты, executor и параметры во всех прогонах.
- В каждом эксперименте доска очищалась; baseline `pointCount=1`.
- Исполнение: 6/6 штрихов, 1524 move calls, `point_step_px=2`, `point_delay_ms=10`.
- Лимит: 6000 points.
- Измеряемый расход: `post.pointCount - pre.pointCount`; сумма sampled `pointDelta` использовалась как независимая проверка согласованности.

Порядок радиусов соответствовал заранее заданным трём блокам:  
1. `1, 5, 10, 15, 20, 25, 30`;  
2. `30, 25, 20, 15, 10, 5, 1`;  
3. `10, 20, 30, 1, 15, 25, 5`.

## 3. Проверка качества данных

По 21 manifest:
- `monitor_capture.status=saved`;
- `chalk_status=exact`, `chalk_counter_consistent=true`;
- `point_delta_matches_chalk=true`;
- `stroke_count=6`, `expected_stroke_count=6`;
- `brush_radius_status=single`, наблюдался только запрошенный радиус;
- `dropped_events=0`;
- `monitor_dropped_events=0`;
- `monitor_error_count=0`;
- executor завершил 6/6 штрихов без ошибки;
- baseline `pointCount=1` для каждого отдельного прогона.

Для всех прогонов Game Monitor зафиксировал примерно 60 FPS, без visibility interruption. Путь в отчётах остаётся `incomplete_until_verified` из-за coalescing промежуточных точек; поэтому длина пути из monitor report не используется как точная мера и не подменяет CHALK.

Сессия Game Monitor: `610c834c-923d-4f60-9770-829103a81d1c`. Каждый из 21 experiment связан с отдельным уникальным run ID. Не относящиеся к матрице pointer-only/ручные события этой длительной сессии не считаются отдельными измерениями.

## 4. Вывод о влиянии радиуса

В контролируемом сценарии из шести длинных горизонтальных штрихов **заметной систематической зависимости расхода CHALK от радиуса 1–30 не обнаружено**. Средние по радиусам находятся в узком интервале 724,00–727,00 CHALK на весь сценарий; все индивидуальные измерения — в интервале 722–728.

Следовательно, для данного сценария увеличение радиуса кисти не приводит к заметному увеличению или уменьшению расхода игрового счётчика. Наблюдаемые различия малы и сопоставимы с разбросом повторов. По этим данным нельзя обосновать множитель расхода, пропорциональный площади кисти или её радиусу.

**Граница вывода:** это результат для одного фиксированного шаблона, одного набора параметров executor и шести длинных прямых штрихов. Он не доказывает независимость CHALK от радиуса для коротких штрихов, диагоналей, кривых, повторного покрытия, частых остановок/старта, других скоростей и других режимов ввода. Для этих геометрий необходимы отдельные серии.

## 5. Практическое следствие для AutoDraw

1. Не рассчитывать расход как площадь кисти × длина пути и не умножать его на функцию радиуса на основании этой серии.
2. Геометрическую длину пути, число move calls, sampled points и фактический CHALK хранить как разные метрики.
3. Для текущего сценария можно использовать эмпирическую опорную величину около **725 CHALK на шесть линий / 2400 логических px**, но только как сценарную оценку с явно указанным разбросом 722–728.
4. В production-планировщике расход должен оцениваться по эмпирической модели, сегментированной по типу геометрии и режиму ввода, а фактическое исполнение контролироваться игровым `pointCount`.
5. Следующий шаг — проверить, насколько результат переносится на короткие штрихи, диагонали, кривые и повторное покрытие. Только после этого объединять данные в общую модель CHALK.
