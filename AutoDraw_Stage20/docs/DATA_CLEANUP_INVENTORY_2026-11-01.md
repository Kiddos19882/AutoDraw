# Инвентаризация и безопасная очистка каталога data

**Дата:** 1 ноября 2026 г.  
**Репозиторий:** `Kiddos19882/AutoDraw`  
**Ветка:** `feature/image-geometry-optimization`  
**Проверенный HEAD до документа:** `01a6d0c0b6f0e133593d53f66a55c98d93676354`  
**Назначение:** определить, какие накопленные результаты тестов можно удалить без потери воспроизводимости и доказательств измерений.  
**Статус:** инвентаризация выполнена по доступному дереву Git, текущим манифестам, анализаторам и документации. Физическая очистка не выполнялась.

## 1. Границы и достоверность инвентаризации

Проверены:
- `docs/FILE_STORAGE_CATALOG.md`, `docs/DATA_FORMATS_AND_PROFILES.md`, `docs/CONFIGURATION_AND_DATA.md`;
- `BRUSH_TEST_RESULTS_ANALYSIS_2026-10-30.md`, `data/results/brush_behavior_tests/ANALYSIS_AUDIT_2026-10-29.md`, `REFACTORING_AUDIT_2026-10-29.md`;
- `GAME_MONITOR_BRUSH_LAB_PLAN.md), `CHALK_GEOMETRY_MATRIX_PLAN.md), результаты радиусной матрицы;
- актуальные исходники UI тестов кистей, CHALK matrix analyzer и storage catalog;
- доступные файлы/манифесты каталога `data/` в указанной ветке.

Это оценка содержимого Git-ветки, а не сканирование локального диска пользователя. Локальные untracked-файлы, файлы portable-сборки и фактический объём папок на диске не видны из GitHub. Поэтому точные размеры в байтах и полный список локальных файлов не заявляются. Поиск GitHub Code Search также не является полным рекурсивным tree listing; количественные итоги ниже приводятся только там, где они подтверждены прежней полной инвентаризацией или конкретными манифестами.

## 2. Подтверждённый состав данных и их ценность

### 2.1. Эксперименты кистей 29–30 октября

Документированные инвентаризации фиксировали:
- 42 файла `experiment.json` в серии 29–30 октября (30 от 29 октября и 12 от 30 октября);
- в другой последующей проверке — 45 `experiment.json` с учётом дополнительных boundary-прогонов;
- семь полноценных экспортов Game Monitor 0.1.2 в `data/test_monitor/`;
- три более ранних JSON-экспорта в `source/game_monitor/`.

Эти наборы нельзя считать мусором только из-за возраста или статуса `legacy_unverified`. Манифесты и изображения использовались для исторического анализа геометрии, ошибки соответствия запрошенного и фактического радиуса, проверки ROI и границ доски. Для старых измерений расхода краски шкала имела статус `inconclusive`, а отдельный ранний сценарий `paint_consumption_long_lines` завершился только на 3 из 12 штрихов. Это ограничивает применимость результатов, но сохраняет их диагностическую ценность.

**Решение:** сохранять манифесты, планы, итоговые изображения доски, относящиеся к ним monitor exports и отчёты. Неподтверждённые данные можно исключать из обучающей/расчётной выборки, но это не основание удалять первичные доказательства.

### 2.2. Boundary probe и проверки Game Monitor

В документации зафиксированы три boundary-прогона: четыре штриха, завершение 4/4, точные дельты CHALK 51/52/52, Monitor без dropped events и ошибок. Изображения и манифесты использовались для визуальной сверки границ и проверки transform.

Каталог `data/result_test_web_socket/` содержит артефакты browser WebSocket smoke test; в WORK_LOG зафиксирован положительный `ready → pong` handshake. Эти файлы подтверждают реальное соединение из игрового iframe и не должны удаляться до тех пор, пока их доказательная роль не сохранена в отдельном архиве.

**Решение:** сохранить исходные manifests, Monitor exports и снимки boundary probe. Smoke-test артефакты можно архивировать отдельно только после проверки, что нужные nonce/response, timestamp и параметры сессии отражены в журнале.

### 2.3. CHALK radius matrix — 21 валидный эксперимент

Серия `chalk-20261101-023127-b85dbb` содержит 21 независимый прогон: семь радиусов × три повтора. Для каждого опыта:
- `monitor_capture.status=saved`;
- `chalk.status=exact`;
- `post.pointCount - pre.pointCount = consumed_points`;
- сумма sampled `pointDelta` согласована с точным CHALK;
- шесть из шести штрихов завершены;
- радиус однозначный;
- dropped events и monitor errors равны нулю.

Пример манифеста подтверждает, что `experiment.json` содержит identity серии, executor report, точный pre/post pointCount, run/session IDs, путь к `monitor_report.json`, фазовые снимки и диагностические метаданные. Поэтому отдельный файл нельзя удалять по одному лишь расширению или размеру.

**Решение:** все 21 каталога опыта сохранять как первичный набор данных. Обязательные части: `experiment.json`, drawing plan, `monitor_report.json`, `after_draw-board.png`, эталон пустой доски и изображения/файлы, на которые ссылается manifest или использованный анализатор. Снимки до/после и полный экран сохранять до создания и проверки отдельного архива с контрольными суммами.

### 2.4. Новая geometry matrix G1/G2

На момент проверенного HEAD инфраструктура G1/G2 и analyzer готовы, но live G1 ещё ожидала запуска. Для будущих результатов analyzer требует:
- `experiment.json` с валидными `chalk_experiment_matrix` metadata;
- точный CHALK и согласованные sampled deltas;
- однозначный радиус и ожидаемое количество штрихов;
- завершённый executor и точные параметры;
- сохранённый `monitor_report.json` для per-stroke breakdown по `strokeId`.

Analyzer специально помечает per-stroke breakdown как incomplete, если файл отчёта отсутствует, число stroke IDs не совпадает с ожидаемым или сумма `pointDelta` не равна точному CHALK.

**Решение:** не удалять `monitor_report.json` даже после генерации сводного JSON: он является первичным источником для повторной проверки per-stroke агрегации. Сводка analyzer не заменяет исходные события.

## 3. Классификация файлов по возможности удаления

### A. Можно удалять при выполнении указанного условия

| Объект | Решение | Условие и основание |
|---|---|---|
| `data/runtime/current_brush_behavior_test.json` | **Можно удалить как runtime-копию** | Только после полного закрытия AutoDraw и проверки, что нет активного исполнения/передачи плана. Аудит рефакторинга установил, что отслеживаемый runtime JSON совпадал по содержимому с одним из сохранённых планов опыта. Это промежуточный файл, а не самостоятельный результат; приложение должно создавать его заново при следующей передаче плана. Перед локальным удалением убедиться, что исходный план сохранён в каталоге соответствующего опыта. |
| Временный токенизированный snippet Game Monitor Bridge в `data/results/brush_behavior_tests/game_monitor_bridge/` | **Можно удалить после остановки collector** | Storage catalog прямо описывает snippet как временный файл, удаляемый при штатной остановке collector. Если он остался после аварийного завершения, удалять только после закрытия collector и проверки, что файл не используется работающим процессом. Не удалять JSON run/session. |
| Пустой placeholder-файл результата (например, нулевой `result.json`) | **Можно удалить только после индивидуальной проверки** | В историческом отчёте указаны пустые `result.json`, которые не являлись результатами тестов. В текущем перечне найденных совпадений точные пути этих placeholder-файлов не установлены. Удалять можно только файл размером 0 байт, если на него нет ссылки из manifest/скрипта/документации и соответствующий сценарий уже не использует его как обязательный выходной путь. |

Эти условия не являются разрешением на массовое удаление одноимённых файлов по шаблону.

### B. Кандидаты на сокращение объёма, но пока НЕ удалять

Удаление без миграции ссылок ломает автономность каталога опыта и повторный анализ. Сначала нужен общий content-addressed архив/ссылочный формат, миграция analyzer и проверка всех manifests. |

Нет подтверждённой миграции, которая сохраняет эту информацию в архиве и оставляет analyzer работоспособным. |

Контекстное сопоставление в отчёте не равно формальной ссылке. Сначала создать индекс соответствий и архив. |

### C. Не удалять

- Все `experiment.json` и планы из валидной CHALK radius matrix.
- Все `monitor_report.json` из валидных CHALK опытов; они нужны analyzer для stroke-level проверки.
- `blank-board-reference.png` и `blank-board-reference.json`: это общий эталон и его metadata, а не дубликаты, подлежащие удалению.
- `after_draw-board.png` для опытов, где он используется для анализа геометрии/видимости/границ.
- `experiment.json`, планы и первичные monitor exports старых серий, пока их результаты отражены в документации только сводно и нет проверенного архива.
- `data/profiles/`, `data/palettes/`, `data/projects/`, калибровочные файлы и пользовательские проекты: это не временные результаты тестов.
- `data/runtime/` как каталог целиком: удалять можно только конкретные устаревшие промежуточные файлы после закрытия приложения, не весь каталог без проверки.
- `session.json` и диагностические данные Game Monitor Bridge до завершения проверки соответствующей сессии и сохранения нужных diagnostics.

## 4. Рекомендуемый порядок безопасной очистки

1. Закрыть AutoDraw и Game Monitor Bridge; убедиться, что не выполняется тест и не создаётся новый capture.
2. Скопировать весь `data/results/brush_behavior_tests/` в отдельный архив перед первой очисткой. Архив должен содержать manifests, планы, monitor reports, изображения и контрольные суммы.
3. Проверить каждый `experiment.json`: извлечь локальные ссылки из `phases.*.files`, `drawing_plan_path`, `execution_report_path`, `game_monitor_report_path` и `monitor_capture.source_path`; проверить, что каждый обязательный файл существует.
4. Составить SHA-256 индекс PNG/JSON. Группировать точные дубликаты по хешу, но не удалять их до перехода на общий asset store и проверки анализатора.
5. Удалить только конкретные stale runtime-файлы, которые не участвуют в текущей сессии и могут быть созданы заново.
6. Для дублирующих run JSON сравнить SHA-256 с `monitor_report.json`; при совпадении сначала убедиться, что в архиве сохранена одна копия и diagnostics не теряются.
7. Перезапустить analyzer на архиве/мигрированном наборе и сравнить число принятых/отклонённых опытов и контрольные суммы результатов.
8. Только после успешной проверки удалить локальные дубли. Не удалять единственные исходные данные и не переписывать manifests задним числом.

## 5. Итоговое решение перед G1

На текущих фактах нет оснований для массового удаления экспериментальных папок или изображений. Наиболее безопасные кандидаты:
1. конкретная runtime-копия `data/runtime/current_brush_behavior_test.json` — после закрытия приложения и подтверждения наличия исходного плана;
2. оставшийся временный токенизированный snippet Bridge — после остановки collector;
3. только те placeholder-файлы, которые фактически имеют 0 байт и не используются никаким активным путём.

Повторяющиеся PNG и вероятные копии Monitor run — это резерв оптимизации хранения, но не немедленно безопасное удаление: сначала требуется миграция ссылок/архива и проверка контрольных сумм.

**Влияние на следующий тест:** перед запуском live G1 не требуется очищать историю CHALK. Достаточно не трогать первичные результаты и при необходимости убрать только неиспользуемые runtime/snippet файлы по условиям выше. Новые G1 результаты должны оставаться самодостаточными: `experiment.json`, drawing plan, `monitor_report.json`, обязательные screenshots и метаданные.

- Не сравнивались SHA-256 всех пар source run / copied monitor report.
- Не проверены все ссылки всех локальных manifests на уровне файловой системы.
