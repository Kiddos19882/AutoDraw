## Критические системные проблемы, сортировка

1. **P0 архитектура выбора траекторий.** Main S5 должен обрабатывать *целые связные области*, включая внутренние крупные зоны, длинные диагонали и узкие участки; локальный start-point greedy/дискретный bank не соответствует этой задаче. До рефакторинга нужен parity test с S4 `paintable_id`, protected contours и original pixels. Выделить одно `region candidate search → footprint risk → global uncovered ledger → fallback`; не дублировать способы расчёта кисти.
2. **P0 семантика покрытия.** Separate: optimistic `potential`, conservative `guaranteed`, source RGB/owner risk и **actual Egret RGBA**; запрет именовать `potential_covered` реальной заливкой. Указывать status `PARTIAL` всякий раз при `uncovered>0`, `unsupported` если не может закрыть. Точки original protected не просто bool input — должны иметь явную стратегию сохранения.
3. **P0 coordinate+native owner.** Текущая карта только source pixel, нет верной Egret calibration, owner MISSING. User S4 visual acceptance (DEC-051) не отменяет это. Никакого сквозного исполнения/Stage6 при false-safe.
4. **P1 производительность.** При миллионах пикселей Python loops × colors × widths × seeds × candidate geometry potentially expensive. Нельзя утверждать slowdown без benchmark. Сначала microbench на независимых synthetic sizes, затем настоящие full DEV telemetry, только потом vectorize/cache/tile.
5. **P1 layering+color ordering.** Source regions могут иметь одинаковый swatch, adjacent different swatches, или important same-gamecolor contours. Отдельное управление order/occlusion; старый order optimizer без native validation не применять поверх принятых исходных границ.
6. **P2 legacy modules.** Старые horizontal planners, FILL001 fixed brush, budget and outline-first — baseline/regression controls и самодостаточная инфраструктура; не удалять и не переписывать ради нового метода.

- build/run unit E2 before full DEV and Egret E3 only with valid owner+calibration; exact CHALK only run-bound game E4.
