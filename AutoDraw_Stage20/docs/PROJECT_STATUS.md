## 3. Текущая техническая инициатива

Основная текущая задача — связать Brush Test UI и Game Monitor, получить достоверную метрику расхода игрового CHALK и подготовить модель, которую AutoDraw сможет использовать до рисования для выбора кистей и траекторий в рамках квоты.

INT-001 завершена: игровой остаток вычисляется как `less = max - pointCount`, где `pointCount` — число принятых точек. Фактический расход эксперимента определяется только точной дельтой `post.pointCount - pre.pointCount`. Контролируемая матрица 1–30 (7 радиусов × 3 повтора) завершена: для фиксированного сценария из шести длинных линий расход составил 722–728 CHALK, систематического влияния радиуса не обнаружено. Подробности и ограничения — `docs/CHALK_RADIUS_MATRIX_RESULTS.md`.

Game Monitor 0.2.1 читает точный счётчик через `BoardPane.max` и `BoardPane.less`; обычный snapshot работает за O(1), полный обход точек оставлен для диагностического режима. Живой Firefox-прогон подтвердил точный baseline/post counter и доставку событий. После исправления корреляции первый run автоматически привязан к executor и manifest: радиус 1, 6 штрихов, `pointCount=1→719`, точный расход 718 CHALK, сумма sampled `pointDelta=718`, потерь и ошибок нет.

Существующие `game_point_calibration.py`, `engine_point_calibration.py` и `board_resource_model.py` дают расчётные оценки, но не заменяют точный engine counter. Они не должны использоваться как источник фактического CHALK до калибровки на серии подтверждённых live-измерений.

INT-002 завершена: определены контракт ресурсного snapshot и протокол baseline/delta. INT-003 частично подтверждена в живом браузере: точный счётчик и события доступны. Она остаётся IN_PROGRESS до A/B/C сравнения Monitor off / 0.1.2 / 0.2.1 и численной оценки overhead/FPS. - исчерпание повторов не должно завершать WebSocket handler; ошибка отмечается в диагностике, новая попытка выполняется на следующем сообщении.

## 14. Межпроцессное владение и recovery

Добавлен lifetime owner lock на каждый block journal. Он удерживается в активном GUI-сеансе и в recovery-сеансе. Второй экземпляр AutoDraw не может пометить живую running-задачу как interrupted, продолжить или закрыть тот же журнал. Если процесс завершился, ОС освобождает lock; следующий экземпляр получает lock и может выполнить штатный interrupted recovery. Resume/close повторно проверяют владение. Для закрытия failed/paused требуется явная проверка доски.
