## 3. Текущая техническая инициатива

Основная текущая задача — связать Brush Test UI и Game Monitor, получить достоверную метрику расхода игрового CHALK и подготовить модель, которую AutoDraw сможет использовать до рисования для выбора кистей и траекторий в рамках квоты.

INT-001 завершена статически. Установлено, что игровой остаток вычисляется как `less = max - pointCount`, где `pointCount` — количество сохранённых точек в `atom.points`. Фактический расход эксперимента следует измерять дельтой `pointCount` между baseline и итогом. Радиус кисти непосредственно в формуле квоты не участвует.

Game Monitor обновлён до 0.2.0: в клиентском bundle статически подтверждены точные поля `BoardPane.max` и `BoardPane.less`; `pointCount=max-less`. `emit()`, wrappers, polling, `status()` и `export()` читают их за O(1), полный обход `atom.points` оставлен только в явном `diagnosticSnapshot()`. Поведенческие Node-тесты добавлены в CI. Живая runtime-сверка и A/B/C overhead по FPS/длительности ещё не выполнены. Автоматическая привязка экспорта к manifest по-прежнему отсутствует.

Уточнение по существующим моделям AutoDraw: помимо legacy px-equivalent расчёта, проект содержит `game_point_calibration.py`, `engine_point_calibration.py` и `board_resource_model.py`. Они дают калиброванные оценки точек, но не прямой engine counter: `game_point_calibration` явно возвращает `is_engine_exact_counter=false`; теоретическая модель использует номинальные 48 FPS и исторические параметры, при этом реальный FPS старой серии не был измерен. Поэтому ни одна из этих оценок пока не заменяет фактическую дельту игрового счётчика.

INT-002 завершена как статическое проектирование контракта ресурсного снимка и протокола baseline/delta. В INT-003 статически подтверждены `BoardPane.max`/`less`, реализован Monitor 0.2.0 с O(1) snapshot и добавлены Node-тесты. INT-003 остаётся IN_PROGRESS: необходимы проверка этих полей в живом iframe и A/B/C замеры без Monitor, с 0.1.2 и с 0.2.0.

Блокер logical→screen частично устранён: Brush Test теперь создаёт logical-планы 420×240, а integrated_app.py преобразует их в screen-local ROI перед загрузкой в Stage6. Добавлены unit- и integration-тесты; обычные local-планы сохраняют прежний путь. Live-проверка фактического ROI и семантики правой/нижней границы ещё не выполнена, поэтому полную матрицу запускать рано. Это ограничение геометрии эксперимента, а не ошибка формулы CHALK.

## 8. Границы достоверности

INT-001 была выполнена статически; на тот момент игровые измерения и A/B Monitor не запускались. INT-003 дополнительно подтвердила в bundle, что `BoardPane.updateLess()` считает количество координат `atom.points`, а `BoardPane.max`/`less` хранят точные целые лимит и остаток. Радиус кисти в формулу не входит: при одинаковом наборе принятых игровых координат прямой расход одинаков; влияние радиуса на площадь покрытия и число требуемых траекторий оценивается отдельно.

Game Monitor 0.2.0 и Node-тесты проверены через GitHub Actions. Это не доказывает runtime-доступность полей на живом iframe и не измеряет FPS. A/B/C-проверка без Monitor / с 0.1.2 / с 0.2.0 остаётся незавершённой.


## 9. Целевая архитектура автоматизированной лаборатории кистей

Создан отдельный документ [BRUSH_TEST_AUTOMATION_VISION.md](BRUSH_TEST_AUTOMATION_VISION.md), описывающий полный целевой цикл от preflight и проверки координат до автоматического исполнения, точных pre/post CHALK snapshots, сохранения dataset и последующей передачи данных модели оптимизации.

Целевые компоненты: Experiment Controller, Plan Generator, Coordinate Transform, Brush Controller, MouseExecutor, независимый Game Monitor, Experiment Recorder и Dataset/Analyzer. Измеряемые штрихи должны выполняться только через MouseExecutor/PyAutoGUI; игровые внутренние методы и счётчики не подменяются тестовым кодом.

Документ фиксирует матрицу радиусов/длин/форм/скоростей/штрихов/перекрытий, минимум три повтора, отдельную A/B/C серию Monitor off / 0.1.2 / 0.2.0, обязательные checkpoints, manifest, fail-safe и критерии валидности.

Это целевая концепция, а не отчёт о готовой реализации. Главный технический блокер перед матрицей — корректное logical→screen преобразование для логической доски 420×240 и экранного ROI. INT-003 остаётся IN_PROGRESS; INT-005 остаётся TODO. Код, тесты и runtime в рамках этой записи не изменялись и не запускались.
